# Task 3 Report — Phase 3 Bootstrap, Exporter, and Flush

## Status

DONE. Phase 3 adds startup reconciliation, deterministic SQLite-to-Markdown
export, durable dirty scheduling, and the native start/status/flush/stop runtime
surface. It intentionally does not add the Phase 4 watcher, `notify`, sync
events, frontend listeners, asset handling, or settings UI.

## Contract delivered

- Startup implements all four SSOT branches: new DB with/without existing
  Markdown, and existing DB with/without existing Markdown. Existing files are
  hash-compared, parsed, merged, or quarantined; empty vaults receive a full
  local export; crash-left dirty rows flush immediately.
- Topic filenames are assigned once from the first local/source title and never
  follow later title edits. `trash.md` uses the reserved non-UUID
  `__yonalist_trash__` metadata identity, so a normal topic cannot claim it.
- Topic and trash snapshots render deterministically, parse back into the exact
  semantic document, publish atomically, record SHA-256 echo hashes, then clear
  only the dirty markers whose captured HLC/fingerprint is still current.
- Dirty scheduling exports after 3 seconds idle or 30 seconds total. Failed
  targets remain scheduled; one failure does not starve healthy targets.
  Explicit flush and stop bypass debounce.
- Local empty-trash and history hard-delete paths record HLC purge tombstones
  before deleting rows. Trash rendering preserves independent deletion-batch
  roots and makes purge evidence durable before a retired topic file is removed.
- Root deletion, purge, restore, and cross-topic movement maintain their former
  and destination topic files. Removal waits for the dependency topic/trash
  export, retries parent-directory durability after an interrupted unlink,
  preserves externally changed source bytes by comparing them with the stored
  export hash, and recreates the original immutable filename on restore.
- Synthetic former-root removal markers are coalesced when the root returns by
  any path, including history/merge rerooting, avoiding stale removal failures.
- The trash lifecycle trigger is installed both for new databases and every
  open of an existing schema-v2 database. One shared purge-evidence helper owns
  tombstone/HLC persistence for repository and history deletion paths.
- `NotesSyncRuntime` is idempotent across repeated start/stop and vault switches.
  The four Tauri commands are registered and granted only to the local main
  window; generated ACL schemas reflect the command permissions.

## Phase boundaries and residual risk

- There is no manual UI verification in Phase 3 because it adds no frontend
  listener or user-visible event surface.
- External edits are preserved during retirement and remain dirty for the Phase
  4 watcher/restart merger to consume.
- Filesystem watching, periodic scan, bounced-copy handling, 500ms frontend
  coalescing, `notes://sync-changed`, and asset-arrival behavior remain Phase 4.
- Asset deduplication/GC, progress events, and settings remain Phase 5.
