# Notes split view Enter 성능 결과

## 결론

Enter가 저장 결과를 기다린 뒤 새 블릿을 그리던 경로를 바꿨다. 이제 명령을
낸 창에 임시 행을 먼저 만들고 커서를 옮긴다. IPC와 파일 저장은 기존
coordinator의 직렬 대기열에서 이어서 처리한다.

체감 지연은 모든 Enter 시나리오에서 크게 줄었다. 보조 창 first-child는
이전 측정에서 커서를 한 번도 잡지 못했지만 이번에는 50회 모두 성공했다.
다만 `keydown → 임시 커서` p95는 `24–33ms`라서 목표인 `16ms` 이하는
달성하지 못했다. 임시 계측 파일과 고정 데이터는 다음 최적화에 쓸 수 있게
남겨 뒀다.

## 구현

- clean split, dirty split, first-child Enter가 명령을 낸 창에만 임시 행을
  즉시 표시한다.
- 새 행은 처음부터 예약된 최종 node ID를 쓴다. 저장 성공 뒤 같은 편집기를
  그대로 채택하므로 다시 마운트하거나 커서를 한 번 더 옮기지 않는다.
- 사용자가 저장 중 새 행에 입력한 제목은 메모리에 두고 실제 node가 생긴
  뒤 기존 draft 저장 경로로 보낸다.
- 연속 Enter는 새 대기열을 만들지 않고 기존 구조 변경 대기열에서 앞선
  임시 node를 직접 의존한다.
- 저장이 확실히 실패하면 임시 행을 없애고 Enter 직전 선택 범위로 돌아간다.
  오류 원인과 되돌렸다는 사실을 계속 보여 주며 복구용 텍스트를 복사할 수
  있다.
- 백엔드 Undo, 영속 outbox, 별도 scheduler는 추가하지 않았다.

## 측정 방법

- 장비: Apple M2 Max, arm64
- 운영체제: macOS 26.5.1 (25F80)
- 런타임: Node 26.4.0, npm 11.17.0, Rust 1.97.0
- 데이터: 전체 text node 5,000개, root 50개, child 4,950개,
  `Benchmark leaf` 1개
- 각 시나리오: 물리 키 입력 워밍업 10회 뒤 50회 측정
- 각 Enter 뒤 실제 `Command-Z`로 구조를 되돌림
- dirty split은 제목 입력과 split을 각각 되돌리려고 `Command-Z`를 두 번
  입력
- 화면 반응은 `keydown → provisional caret`, 저장은
  `provisional caret → authoritative settlement`으로 분리

고정 데이터 서명은 측정 전후 모두 `5000|50|4950|1`이었다.

| 창 | 이전 | 변경 후 | p95 변화 |

저장 전체 시간은 시나리오에 따라 이전과 비슷하거나 변동이 있다. 이번

시간을 사용자 입력 경로에서 떼어 낸 것이 핵심이다.

## 남은 한계

- 60Hz 한 프레임 목표인 p95 16ms는 아직 넘는다. 다음 작업은 명령을 낸 창
  안에서 행 계산, context 전달, DOM 반영 중 어느 구간이 8–17ms를 더 쓰는지
  React profile로 좁히는 것이다.
- renderer crash, 강제 종료, 전원 손실까지 보장하려면 영속 outbox가
  필요하다. 이번 범위에는 포함하지 않았다.
- 저장 결과가 불명확한 오류는 기존 authority recovery 화면과 쓰기 차단
  경로를 그대로 쓴다.
