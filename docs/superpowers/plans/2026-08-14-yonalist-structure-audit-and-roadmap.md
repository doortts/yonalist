## 1. 핵심 판정

**v2 코드베이스는 방향이 옳고 품질도 평균을 크게 웃돈다. 대규모 재작성은 필요 없다.** 순수 도메인 크레이트, 타입화된 에러, 의존 방향 자동 검사를 갖춘 구조라 리팩터링은 국소 수술로 끝난다.

급한 것은 코드가 아니라 결정 3건이다.

1. 지향점인 "텍스트 파일 = 진실 소스"가 정작 출하되는 v2에는 없다. 완성된 파일 동기화 파이프라인은 동결된 v1 안에 잠들어 있고, parity matrix에서는 "승인된 제외" 항목이다.
2. 저장소 Rust의 89%, 프런트엔드의 84%가 그 동결된 v1이다.
3. CI는 레거시 트리만 검사한다. v2 게이트는 전부 수동이다.

### 저장소 지도 — 한 저장소, 두 개의 앱

루트 `src/` + `src-tauri/`(v1)와 `apps/desktop/` + `crates/`(v2)는 계층 관계가 아니라 코드를 한 줄도 공유하지 않는 별개 애플리케이션이다. `apps/desktop/src-tauri/Cargo.toml`에 `yonalist` 의존이 없고, `checkV2Architecture.mjs`는 v2가 레거시 프런트엔드를 import하면 오류를 낸다.

| | v1 (루트) | v2 (apps/desktop + crates) |
|---|---|---|
| 역할 | 동결. parity matrix의 행동 기준으로만 참조 | 출하 제품 (`com.doortts.yonalist.v2`) |
| 규모 | TS 197,027 LOC / Rust 121,517 LOC | TS 37,578 LOC / Rust 1,550 + 15,844 LOC |
| IPC 명령 | 79개 | 20개 |
| 저장 모델 | markdown vault SSOT + SQLite 캐시 (HLC 동기화 완비) | **SQLite 단독** (`notes-v2.sqlite`) |
| Cargo | 워크스페이스에서 `exclude` (`Cargo.toml:9`) | 워크스페이스 멤버 5개 + 어댑터 |
| CI | `ci.yml`이 검사하는 유일한 대상 | 어떤 검사도 CI에 없음 |
| 마지막 커밋 | 2026-07-29 | 2026-08-14 |

기본 실행 명령(`npm run tauri:dev`)은 v2를 띄우지만 기본 `npm test` / `build` / `lint`는 여전히 v1을 가리킨다.

### v2 구조 요약

백엔드는 육각형 계층이다. `apps/desktop/src-tauri`(어댑터, IPC 20개, `StartupGate`로 비차단 부팅) → `notes-application`(포트·계약, ts-rs로 TS 타입 생성, `NotesError` 12종) → `notes-core`(순수 도메인, 의존성은 serde/thiserror뿐) → `notes-sqlite`·`notes-export`(단일 워커 스레드 + mpsc, STRICT 테이블, revision 낙관적 동시성).

프런트엔드는 라이브러리 없이 만든 저장소 클래스 + `useSyncExternalStore` 조합이다. 노드는 트리가 아니라 평탄 배열(`NoteView[]`, 부모 포인터 + `sortKey` 정수)로 두고 트리 구조는 `OutlineIndex`가 필요할 때 파생시킨다. 구독은 셸 / 아웃라인 / 노드별 3단계로 나눠 행 단위 리렌더를 막는다. 되돌리기는 Rust가 실제 스택을 소유하고 프런트는 그룹 경계와 커서 복원만 맡는다.

### 결함이 아닌 것 (기록용)

**이미지 중복 검사의 재독은 결함이 아니다.** 1차 문서는 이 재독을 P2 항목으로 올렸다(`image_assets.rs:76-118`, "sha256이 이미 같음을 증명했는데 다시 읽는다"). 전제가 틀렸다. 해시는 방금 받은 **새** 바이트에서 계산했고, 디스크에 이미 있는 **기존** 파일이 그 내용과 같다는 증명은 어디에도 없다. 그 재독 + byte 비교가 기존 자산의 손상(잘림, 비트 부패, 외부 도구의 덮어쓰기)을 잡는 유일한 지점이고, 불일치면 조용히 넘기지 않고 에러를 낸다. 제거하면 손상된 파일 위에 새 노드를 얹는다. 20MB 재독이 실제로 문제가 되면 전체 비교 앞에 파일 크기 비교를 두는 정도가 상한이다.

`user_version != 1`이면 하드 에러를 내는 무마이그레이션 구조(`crates/notes-sqlite/src/schema.rs:78-82`)는 릴리즈 전 스키마 동결이라는 기존 결정과 일치한다. 다만 **첫 릴리즈 직전에** 빈 마이그레이션 사다리 골격을 넣는 일은 그 시점의 필수 항목으로 잡아 둔다(§8). 사다리 없이 릴리즈하면 다음 스키마 변경이 기존 설치를 전부 벽돌로 만든다.

`checkV2Architecture.mjs`가 내는 500/800줄 초과 경고 15건은 advisory여서 아무도 실패시키지 않는다. 목록이 곧 P1-4/P1-9 대상이다(`outlineKeyboard.ts` 745줄, `NotesOutline.tsx` 726줄, `App.tsx` 592줄, `outlineSupport.ts` 578줄, `notesStore.ts` 516줄).

## 4. 파일 SSOT 정합성 — Logseq 교훈과 포팅 계획

> **2026-08-14 전제 교체:** 이 절은 "단일 기기 데스크톱이 기본"을 해자 논거로 썼는데, 제품 목표가 **멀티 디바이스**로 확정됐다. v1 sync는 애초에 멀티 디바이스용으로 설계·구현돼 있었으므로(스펙 §0) 포팅 자산 목록은 유효하다. 확장된 계획 — 업계 조사, 아키텍처 선택, 워커 접합, undo 배리어, 마일스톤 M0~M6 — 은 [파일 SSOT 포팅 계획](2026-08-14-file-ssot-multi-device-port.md)이 이어받는다. 아래 미해결 4건 중 1번(undo×병합)과 4번(증분 재색인)의 답도 그 문서 §3.3·§6에 있다.

parity matrix에서 "Vault Markdown 동기화"(`feature-parity-matrix.md:56`)는 승인된 제외 항목이었다. 그 이월이 이제 만기다. 지향점을 유지하는 한 v2에 동기화 파이프라인이 없는 현 상태는 제품이 지향과 다른 저장 모델로 굳어 가는 중이라는 뜻이고, 데이터가 쌓일수록 전환 비용이 커진다.

### Logseq가 파일을 버린 이유가 우리에게 유리한 이유

Logseq는 2026-07 "Logseq 2.0"에서 파일 기반(OG)을 유지보수 모드로 내리고 SQLite를 정본으로 삼았다. 그런데 그들이 밝힌 실패 원인을 뜯어 보면 파일 자체가 아니라 설계 실수 쪽이다.

- 정체성이 본문 텍스트 안에만 있었다. `id::` 속성이 사용자 파일을 오염시키면서도 외부 편집 한 번에 블록 정체성이 깨졌다.
- 다중 기기 동시 쓰기가 데이터 손실의 실제 진원지였다. 여러 클라이언트가 같은 파일을 통째로 재작성했다.
- 블록 단위 편집을 파일에 직결해 키 입력마다 파일을 재작성했고, 시작할 때 전체를 재파싱해서 2천 페이지에 4~10분이 걸렸다.
- 그 결과 grep·git·"LLM에게 노트 폴더를 보여 주는" 워크플로를 잃었고, Markdown Mirror(단방향)와 CLI라는 별도 기능으로 재건축해야 했다. DB에서 내보낸 markdown은 구조적으로 손실이 있다고 스스로 문서화했다.

우리 설계는 이 함정을 대부분 비켜 간다. 단일 기기 데스크톱이 기본이라 동시 쓰기 문제가 없고, SQLite 캐시가 편집 입도를 흡수해 디바운스된 원자적 쓰기만 파일에 닿으며, 파일이 정본이므로 충실도는 구성상 보장된다(캐시는 언제든 버리고 재구축). Logseq가 기능으로 되사야 했던 것들 — grep, git, 파일시스템이 곧 API — 을 우리는 공짜로 갖는다. 이게 이 앱의 해자다.

### 미해결 설계 문제 4건 (포팅 착수 전에 답이 나와야 한다)

1차 문서는 이 마일스톤을 "포팅"이라 부르고 크기를 비웠다. 그 단어가 신규 설계 4건을 감추고 있다.

1. **되돌리기와 외부 편집의 화해.** 되돌리기 스택은 Rust가 소유하고 DB 상태를 되돌린다. watcher가 외부 파일 편집을 병합한 뒤, 스택에 이미 쌓인 항목들은 어떤 상태로 되돌아가는가? 사용자가 손대지 않은 편집을 되돌리기가 지워 버리는 경로가 생긴다. **이 항목이 SSOT 마일스톤의 최대 난제이고 1차 문서에 아예 없었다.** 후보: 외부 병합이 들어오면 스택을 자르기, 병합 지점에 배리어를 두기, 되돌리기를 병합과 같은 LWW 규칙 아래 넣기. 셋 다 사용자에게 보이는 행동이 다르니 결정이 필요하다.
2. **정체성 주석의 관용적 재대응.** v1 파일 포맷은 노드 정체성을 `<!-- yid: uuid t: hlc -->` 주석으로 파일 안에 둔다. Logseq의 `id::`와 같은 지점이다. 외부 편집기가 이 주석을 지우거나 망가뜨릴 때 텍스트 유사도나 위치로 기존 id에 다시 잇는 경로를 명시적 요구사항으로 넣는다. Logseq는 이게 없어서 정체성이 깨졌다.
3. **충돌 로그의 읽기 경로.** v1은 `merger.rs:2048`에서 로그를 쓰기만 하고 IPC로도 UI로도 노출하지 않아, 사용자가 덮어쓰인 편집을 복구할 데이터가 묻혀 있었다. 게다가 정리 경로가 없어 무한히 쌓인다. "신경 안 써도 잘 동작하는 앱"이라면 충돌은 조용히 기록하되 필요할 때 꺼내 볼 수 있어야 한다.
4. **증분 재색인의 정확성 기준.** mtime/hash 기반이 원칙인데, mtime이 거짓말하는 경우(클라우드 동기화 폴더, 시계 역행)의 안전망을 정한다. v1의 60초 전체 재스캔이 그 자리였지만 대형 vault에서 비용을 재봐야 한다.

### 포팅 자산과 순서

v1 파이프라인은 스텁이 아니라 완성돼 있고 이례적으로 엄격하다. SQL 트리거 기반 HLC 스탬핑·dirty 추적(`src-tauri/src/notes/schema.rs:208-228`), 3초/30초 디바운스, 렌더→재파싱 자가 검증, fsync + NOREPLACE 원자적 쓰기, notify 감시자 + 60초 전체 재스캔 안전망, 노드 단위 HLC LWW 병합(고아·순환 파킹 포함), 90일 tombstone GC, sha256 자산 GC를 모두 갖췄다. v2의 육각형 구조에 맞춰 `notes-sync` 크레이트로 옮긴다.

크기: **L (여러 주).** 위 4건이 신규 설계이고, 스키마 추가(dirty 추적, HLC 스탬프)가 필요하며, 포팅 대상이 30k줄이다. P0/P1의 S/M과 같은 축으로 읽으면 안 된다.

1. `file_io.rs` 원자적 쓰기 계층. 그대로 이식 가능한 최상급 자산이다.
2. exporter + 자가 검증. 이식하면서 알려진 결함을 함께 고친다 — `exporter.rs:262`의 dirty 노드당 N+1 조회(1,000노드 편집이면 약 3,000 추가 질의, 디바운스 만료까지 1Hz로 반복 평가)와 `runtime.rs:776`의 1초 폴링.
3. watcher + 부트스트랩 조정. 단 **시작 시 전체 재파싱 금지** — mtime/hash 기반 증분 재색인을 원칙으로 삼는다(미해결 4번). Logseq 최대 성능 실패 지점이다.
4. HLC LWW merger + 충돌 로그 읽기 경로(미해결 3번) + 되돌리기 화해(미해결 1번).

포팅 시 함께 확인할 v1 `ponytail:` 표시 7건: `exporter.rs:1713`(잠금 아래 세그먼트 쓰기), `repository.rs:308`(테스트가 레거시 vault 경로 유지), `watcher.rs:574`(병합과 회수 I/O 미분리), `runtime.rs:776`(폴링), `asset_gc.rs:34`(24시간 하드코딩), `asset_gc.rs:3146`(해시 불일치가 치명적), `merger.rs:1665`(병합 topic 서브트리만 재스캔).

또 하나: `src-tauri/src/notes/mod.rs:19`의 `#[allow(dead_code)]`가 30k줄 `sync` 모듈 전체를 덮고 있고 주석은 "Phase 1 wires pure file-format types ahead of the later runtime phases"라 주장하지만 실제로는 `lib.rs:36-37`이 명령을 등록해 쓰고 있다. v1에서 진짜 죽은 코드를 찾는 유일한 lint를 막고 있으므로, 포팅 범위를 잡기 전에 이 속성만 떼고 경고를 확인하는 편이 좋다.

## 5. Workflowy · Logseq DB 비교 — 기능 보강 우선순위

철학이 "간결한 화면, 필요할 때만 등장, 알아서 잘 동작"이므로 기준은 기능 수 경쟁이 아니라 감각 재현이다.

| Workflowy를 정의하는 것 (중요 순) | v2 상태 | 비고 |

| 1. 줌 + 브레드크럼 + 하나의 무한 트리 | 있음 | 완성. 분할 창은 Workflowy에 없는 우리 쪽 우위 |
| 2. 입력 즉시 필터되는 검색, **조상 사슬 보존** | 부분 | 사이드바 검색 패널은 있으나 아웃라인 제자리 필터가 아니다. **최대 격차** |

### Logseq DB에서 가져올 것과 버릴 것

- **버릴 것: 타입 속성·온톨로지·질의 언어.** Logseq DB의 간판 기능이지만 전부 "화면은 간결하게, 사용자는 신경 끄게"와 반대 방향이다. Workflowy가 이걸 전부 안 하고도 제품인 이유가 우리 철학의 근거다.
- **가져올 것: 태그를 본문 텍스트 밖에 렌더링하는 절충.** 의미는 부여하되 문법 소음은 없앤다. 현 tag-spec이 픽셀 불변 원칙 때문에 pill 렌더링을 보류한 결정과 공존 가능한 장기 참고안이다.
- **가져올 것: 정체성과 undo는 DB 계층에서.** undo를 파일 diff로 만들지 않는다(Logseq가 실명한 실패 지점). 우리 구조는 이미 이렇게 돼 있으니 유지한다 — 단 §4 미해결 1번이 이 결정의 대가다.
- **기록해 둘 것: 파일 접근성은 이제 시장의 기본 기대치다.** Logseq 사용자 이탈 사유 1위가 "일반 텍스트 포기"였고 "LLM에게 노트 폴더를 보여 준다"가 표준 워크플로가 됐다. 파일 SSOT 완성은 기능이 아니라 포지셔닝이다.

## 6. 성능 기준선

경쟁 제품의 실측 약점이 목표선을 정해 준다. Workflowy는 Electron 데스크톱이 대형 계정에서 버벅이는 것이 가장 약한 고리고(5만+ 항목대 불만 다수), Logseq 파일판은 시작 시 전체 재파싱으로 무너졌다.

|---|---|---|---|
| 부트스트랩 50k 노드 | < 2s | SSOT 포팅 전까지 유지 | 포팅 후에는 이 계약이 **재는 대상 자체가 바뀐다**(파일 스캔 포함 여부). 그때 계약 문구를 다시 쓴다 |

성능 계약은 `--features bench-fixtures`로 옵트인이라 평시 `cargo test --workspace`가 건너뛴다. P0-2의 결정 2번이 이 처분을 다룬다.

## 7. 권고 로드맵

1. **P1 구조 수술** (4 → 5 → 8 → 7 → 6 → 9). 사용자 지시로 지금 착수. 앞의 다섯은 서로 파일이 겹치지 않고, 9는 178파일을 옮기므로 맨 마지막이다. 진행은 §9.
2. **게이트 복구** (P0-2). CI를 v2로 올리고 그 안의 결정 3건을 함께 처리한다. P1 뒤로 놓는 이유는 P1-9가 경로를 전부 바꿔서 워크플로 파일을 두 번 쓰게 되기 때문이다.
3. **태그 작업 완주.** tag-spec의 자동완성 + 제자리 필터가 Workflowy 최대 격차를 직접 메운다. 새 폴더 구조 위에서 시작한다.
4. **스키마 창 정리** (§8). 릴리즈 전 마지막 기회에 스키마를 건드리는 일을 한 번에 몰아 넣는다.
5. **파일 SSOT 포팅 마일스톤** (L). `notes-sync` 크레이트로 v1 파이프라인 이식(§4 순서). 미해결 설계 4건을 먼저 정리한다. 이 앱의 정체성이 걸린 항목이라 태그 이후 최우선 대형 작업으로 권고한다.
6. **v1 아카이브 실행** (P0-3). **SSOT 포팅이 끝난 뒤**에 태그 + 브랜치 보존 후 main에서 제거한다. 1차 문서는 이걸 2순위로 뒀는데, 포팅 원본 30k줄을 포팅 전에 main에서 지우면 이식 내내 태그 체크아웃으로 오가야 하고 v1을 실행해 행동을 비교하는 oracle 경로도 불편해진다. 동결 코드는 아무도 만지지 않으니 부피 8할 제거가 급할 이유가 없다.
7. **감각 보강.** 검색 제자리 필터(조상 보존) → Cmd+K 점프 팔레트 → 전역 빠른 캡처. 셋 다 "감춰 놓되 필요할 때 등장" 철학의 직계 후손이다.
8. **보류 목록 유지.** 미러·보드·표·타입 속성은 SSOT 안착과 위 감각 보강이 끝날 때까지 착수하지 않는다.

## 8. 스키마 창 — 릴리즈 전에 한 번에 몰 것

`schema.rs:78-82`가 `user_version != 1`을 하드 에러로 막는다. 즉 스키마를 바꾸는 모든 일은 첫 릴리즈 전에 끝나거나, 마이그레이션 사다리를 먼저 깔아야 한다. 1차 문서는 이 항목들을 서로 다른 절에 흩어 놓아 의존 관계가 보이지 않았다. 한 흐름으로 묶는다.

| 스키마를 건드리는 일 | 어디서 왔나 |
|---|---|
| 뷰포트 정렬 키 물질화 | P1-6에서 분리 (접힌 가지 가지치기만 P1에서 하고, 물질화는 여기로) |
| dirty 추적 + HLC 스탬프 컬럼·트리거 | SSOT 포팅 (§4) |
| 빈 마이그레이션 사다리 골격 | 릴리즈 직전 필수 항목 |

순서: 사다리 골격을 **먼저** 깐다. 그러면 나머지 둘의 순서 제약이 풀리고, 릴리즈 후 스키마 변경도 벽돌을 만들지 않는다.
