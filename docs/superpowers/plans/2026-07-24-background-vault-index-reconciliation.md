# Background Vault Index Reconciliation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** GitHub Inbox가 기존 SQLite 인덱스를 먼저 표시하고 모든 Vault 파일·SQLite 작업을 Tauri main/IPC 이벤트 루프 밖에서 실행한 뒤, 변경된 Markdown만 백그라운드에서 정합화하도록 만든다.

**Architecture:** 기존 Tauri Vault 명령은 동기 본체와 얇은 async `spawn_blocking` wrapper로 분리한다. Rust는 metadata manifest 비교, 변경 파일의 hash/frontmatter 추출, 원자적 candidate/index 투영을 담당하고, 기존 `yaml` 패키지를 쓰는 Vite module worker가 YAML만 파싱한다. React는 cached items와 outbox를 독립적으로 로드하고 실제 reconcile 변경이 있을 때만 item index를 한 번 다시 읽는다.

**Tech Stack:** Rust 1.97, Tauri 2.11, rusqlite 0.40, React 19, TypeScript 6, Vite 8 module worker, Vitest 4, 기존 `yaml` 2.9

## Global Constraints

- 새 runtime dependency, file watcher, polling, streaming, 행별 React 갱신을 추가하지 않는다.
- GitHub Vault 파일·manifest/index 명령의 `std::fs`, metadata, hash, `connect_index_db`, `rusqlite` 호출은 모두 `tauri::async_runtime::spawn_blocking` 안에서 실행한다.
- `list_markdown_files`, Tauri 전체 본문 scan, `rebuildVaultStateFromMarkdown`, 사용되지 않는 replace 명령은 최종 결과에서 제거한다.
- Rust scan 응답은 Markdown 본문을 포함하지 않고 `relative_path`, `size`, 10진 문자열 `modified_ns`, `content_hash`, frontmatter만 포함한다.
- YAML은 UI thread가 아니라 Web Worker에서 기존 `yaml` 패키지로 파싱한다.
- 파일 경로와 Markdown 본문을 performance log에 기록하지 않는다.
- 기존 index 표시 p95는 100ms 이하, reconcile로 인한 50ms 이상 main-thread long task는 0회, React 적용 p95는 16ms 이하이다.
- 30초 인위 지연 중 `session_token_storage_backend` IPC 100회의 p95는 50ms 이하, max는 100ms 이하이며 5초 main-thread sample의 `read`, `read_dir`, `rusqlite` stack은 0개여야 한다.
- 현재 규모 fixture는 Markdown 164개/index 66개이며 warmup 5회 뒤 31회 측정한다.

fn command_source<'a>(source: &'a str, command: &str) -> &'a str {
    let declaration = format!("async fn {command}(");
    let start = source
        .find(&declaration)
        .unwrap_or_else(|| panic!("{command} must be async"));
    let tail = &source[start..];

        .find("\n}\n")
        .unwrap_or_else(|| panic!("{command} wrapper must end"));

}

```rust
async fn run_vault_blocking<T, F>(operation: F) -> Result<T, String>
where
    T: Send + 'static,
    F: FnOnce() -> Result<T, String> + Send + 'static,
{
    tauri::async_runtime::spawn_blocking(operation)
        .await
        .map_err(|error| error.to_string())?
}
```

    vault_path: String,

    run_vault_blocking(move || list_vault_item_index_inner(vault_path)).await

#[tauri::command]
async fn persist_vault_documents(
    vault_path: String,
    documents: Vec<VaultPersistDocument>,

    run_vault_blocking(move || persist_vault_documents_inner(vault_path, documents)).await

#[tauri::command]
async fn move_text_file(
    vault_path: String,
    from_relative_path: String,
    to_relative_path: String,

```rust
fn file_modified_ns(metadata: &fs::Metadata) -> Result<i64, String> {
    let nanos = metadata
        .modified()
        .map_err(|error| error.to_string())?
        .duration_since(std::time::UNIX_EPOCH)
        .map_err(|error| error.to_string())?
        .as_nanos();
    i64::try_from(nanos).map_err(|_| "File modified time is out of range.".to_string())
}
```

migration statement 뒤 `backfill_legacy_item_candidates(&Connection)`를 호출한다. 이 함수는 `item_candidate_json IS NULL`인 `document_hashes` 행과 같은 `relative_path`의 `item_index` record만 기존 `VaultItemIndexRecord`로 읽어 JSON을 채운다. 이미 candidate가 있거나 경로가 일치하지 않는 행은 바꾸지 않는다.

- [ ] **Step 5: item index upsert가 candidate와 실제 metadata를 함께 확정하도록 구현한다**

transaction을 열기 전에 각 record를 JSON으로 serialize하고 실제 파일 metadata를 읽는다.

```rust
struct PreparedItemCandidate {
    record: VaultItemIndexRecord,
    candidate_json: String,
    size: i64,
    modified_ns: i64,
}

fn prepare_item_candidate(
    vault_path: &str,
    record: VaultItemIndexRecord,
) -> Result<PreparedItemCandidate, String> {
    let path = resolve_vault_file(vault_path, &record.relative_path)?;
    let metadata = fs::metadata(path).map_err(|error| error.to_string())?;
    Ok(PreparedItemCandidate {
        candidate_json: serde_json::to_string(&record).map_err(|error| error.to_string())?,
        size: i64::try_from(metadata.len())
            .map_err(|_| "File size is out of range.".to_string())?,
        modified_ns: file_modified_ns(&metadata)?,
        record,
    })
}
```

`upsert_vault_item_index_inner`는 prepared vector를 만든 뒤 transaction에서 기존 `upsert_item_index_record`와 다음 UPDATE를 연속 실행한다.

```sql
UPDATE document_hashes
SET item_candidate_json = ?3, size = ?4, modified_ns = ?5
WHERE vault_root = ?1 AND relative_path = ?2
```

파일 metadata 준비가 하나라도 실패하면 transaction을 열지 않고 기존 index/candidate를 유지한다. UPDATE affected row가 1이 아니어도 transaction을 rollback해 index만 있고 candidate가 없는 상태를 만들지 않는다.

```rust
fn frontmatter_only(contents: &str) -> (Option<String>, bool) {
    let Some(rest) = contents.strip_prefix("---\n") else {
        return (None, false);
    };
    let Some(close) = rest.find("\n---\n").or_else(|| rest.strip_suffix("\n---").map(str::len)) else {
        return (None, true);
    };
    (Some(rest[..close].to_string()), false)
}
```

- [ ] **Step 4: metadata/CAS 검증과 짧은 IMMEDIATE transaction을 구현한다**

transaction 전에 변경 경로가 scan의 `(size, modified_ns)`와 같은지, removed path가 여전히 없는지 확인한다. transaction을 연 뒤 `document_hashes` 현재 행이 `expected`와 정확히 같은 경로만 적용한다.

모든 `modified_ns` payload는 transaction을 열기 전에 `parse::<i64>()`로 검증한다. 빈 문자열, 숫자가 아닌 값, i64 범위 밖 값이 하나라도 있으면 어떤 DB 변경도 수행하지 않는다.

```sql
BEGIN IMMEDIATE;

INSERT INTO document_hashes (
  vault_root, relative_path, content_hash, size, modified_ns,
  item_candidate_json, updated_at, last_seen_at
)
VALUES (?1, ?2, ?3, ?4, ?5, ?6, ?7, ?7)
ON CONFLICT(vault_root, relative_path) DO UPDATE SET
  content_hash = excluded.content_hash,
  size = excluded.size,
  modified_ns = excluded.modified_ns,
  item_candidate_json = excluded.item_candidate_json,
  updated_at = excluded.updated_at,
  last_seen_at = excluded.last_seen_at;

DELETE FROM document_hashes
WHERE vault_root = ?1 AND relative_path = ?2;

DELETE FROM item_index;
-- validated dedupe winner마다 기존 upsert_item_index_record 호출
COMMIT;
```

CAS가 실패한 경로는 적용하지 않고 `deferred`만 증가시킨다. 유효 upsert/delete가 0이면 transaction과 item projection을 생략한다.

function parseInWorker(
  vaultRoot: string,
  changes: VaultIndexScanChange[]
): Promise<VaultIndexWorkerResult> {
  const worker = new Worker(new URL("./vaultIndex.worker.ts", import.meta.url), {
    type: "module"
  });
  const id = 1;
  return new Promise((resolve, reject) => {
    worker.onmessage = (event) => {
      if (event.data.id !== id) return;
      worker.terminate();
      resolve(event.data.result);
    };
    worker.onerror = (event) => {
      worker.terminate();
      reject(new Error(event.message || "Vault index worker failed."));
    };
    worker.postMessage({ id, vaultRoot, changes });
  });
