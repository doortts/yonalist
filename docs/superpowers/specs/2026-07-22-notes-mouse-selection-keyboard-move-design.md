# Notes 마우스 선택 후 키보드 이동 설계

## 계약

| 항목 | 내용 |
| --- | --- |
| 목표 | 마우스로 만든 블릿 선택을 포커스 위치와 무관하게 이동 단축키로 옮긴다. |
| 완료 조건 | macOS `Ctrl+Shift+↑/↓`와 `Cmd+Shift+↑/↓`, Windows/Linux `Alt+Shift+↑/↓`가 블릿 버튼에 포커스가 있어도 선택 전체를 한 단계 이동한다. 메뉴의 단축키 표시가 실제 동작과 일치한다. |
| 비대상 | 마우스 선택 방식, 드래그앤드롭, 선택 모델, 이동 순서 계산, Rust/IPC/SQLite 변경은 포함하지 않는다. |
| 경계 | React 키보드 이벤트, 기존 선택 명령 라우터, 블릿 메뉴 단축키 표시만 변경한다. |
| 직접 확인 | 마우스로 여러 블릿을 선택하고 포커스가 블릿 버튼에 남은 상태에서 위·아래 이동 단축키를 누른다. |

## 확인된 원인

선택 이동 키는 `OutlineNodeRow`의 제목 편집기 `onKeyDown`에서만 선택 명령으로
변환된다. 마우스 선택 뒤 포커스가 블릿 버튼처럼 제목 편집기가 아닌 곳에 있으면
이 경로가 실행되지 않는다. 최근 드래그 선택 수정은 포인터를 놓은 뒤 제목에 포커스를
돌려주지만, 선택 명령의 동작이 여전히 포커스 복구 성공에 의존한다.

또한 실제 이동 해석기는 Workflowy 방식인 macOS `Ctrl+Shift+↑/↓`, 그 외 플랫폼
`Alt+Shift+↑/↓`를 사용하지만 블릿 메뉴는 각각 `⌘⇧↑/↓`,
`Ctrl+Shift+ArrowUp/Down`을 표시한다.

## 선택한 설계

아웃라인 콘텐츠의 기존 키다운 캡처 단계에서 살아 있는 블릿 선택과 플랫폼별 이동
키를 확인한다. 이동 키면 기본 동작과 하위 전파를 막고 기존 선택 명령 라우터의
`moveUp` 또는 `moveDown`을 실행한다. 따라서 제목, 블릿 버튼 또는 다른 아웃라인
요소 중 어디에 포커스가 있어도 동일한 권한 준비·배치 이동·Undo 경로를 사용한다.

플랫폼별 이동 키 해석은 `outlineKeyboard`의 순수 함수 하나를 공유해 행 키다운과
아웃라인 캡처가 서로 다른 키를 해석하지 않게 한다. IME 조합과 `Process`는 소유하지
않고, 자동 반복은 소비만 하여 중복 이동을 방지한다.

macOS에서는 기존 `Ctrl+Shift+↑/↓`와 추가 별칭인 `Cmd+Shift+↑/↓` 중 정확히 하나의
주 수정키를 누른 경우를 허용한다. `Ctrl`과 `Cmd`를 동시에 누른 조합은 오입력으로
간주해 소유하지 않는다. 메뉴와 `aria-keyshortcuts`에는 두 대안을 모두 표시한다.

블릿 메뉴의 Move up/down 표기는 같은 실제 키로 고친다.

## 검토한 대안

- 포인터 종료마다 제목에 포커스를 강제하면 현재 증상 일부는 해결되지만 새로운
  마우스 선택 경로가 생길 때마다 같은 문제가 반복된다.
- 블릿 버튼의 `onKeyDown`만 보강하면 다른 비편집 포커스에서는 여전히 실패한다.
- 아웃라인 캡처는 선택 명령의 실제 소유 범위와 같고 기존 라우터를 재사용하므로
  포커스 복구를 안전망으로만 남길 수 있다.

## 검증

1. 마우스 Shift+클릭으로 범위를 선택하고 블릿 버튼 포커스에서 이동하는 통합 테스트.
2. macOS의 Ctrl/Cmd 별칭과 Windows/Linux 메뉴 표기가 순수 키 해석과 일치하는 테스트.
3. IME와 자동 반복이 명령을 중복 실행하지 않는 단위 테스트.
4. 전체 프런트엔드 테스트, 린트, 빌드, `git diff --check`.
