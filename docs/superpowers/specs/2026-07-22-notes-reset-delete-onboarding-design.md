# Notes 초기화·전체 삭제·안내 노트 복구 설계

## 목표

개발 단계에서는 Notes 스키마 마이그레이션을 지원하지 않는다. 대신 구형 또는
손상된 개발용 SQLite 저장소를 명시적으로 초기화할 수 있게 하고, 전체 Notes
데이터 삭제 기능은 유지한다. 초기화 또는 삭제 후 불러올 수 있는 Notes 동기화
파일이 하나도 없으면 기본 안내 노트 세트를 자동으로 생성한다.

## 완료 조건

- 개발 환경의 설정 화면에서 `Notes DB 초기화`를 실행할 수 있다.
- 일반 Notes 초기화가 구형 DB 검사에서 실패한 상태에서도 DB 초기화를 실행할 수
  있다.
- DB 초기화는 현재 app-local SQLite와 구형 vault-local SQLite를 제거하지만 Notes
  동기화 Markdown 파일과 첨부파일은 보존한다.
- DB 초기화 후 유효한 동기화 파일이 있으면 이를 가져오며 기본 안내 노트는 남지
  않는다.
- DB 초기화 후 가져올 수 있는 동기화 파일이 없으면 기본 안내 페이지 한 개와 그
  하위 안내 블릿 여섯 개를 생성한다.
- 기존 `전체 Notes 데이터 삭제` 기능은 유지한다.
- 전체 삭제는 Notes SQLite, Yonalist가 소유한 Notes 동기화 Markdown 파일,
  Notes 첨부파일과 Notes 전용 휴지통 데이터를 제거한다.
- 전체 삭제는 vault 안의 사용자 일반 파일과 앱 설정을 제거하지 않는다.
- 전체 삭제 직후 새 현재 스키마 DB를 만들고 기본 안내 노트 세트를 생성한다.
- 성공 후 현재 창에서 Notes 작업공간을 다시 불러와 안내 노트 또는 동기화된 노트를
  바로 표시한다.
- 구형 스키마를 현재 스키마로 변환하거나 구형 DB의 내용을 자동 복구하지 않는다.

## 사용자 동작

### Notes DB 초기화

개발 빌드에서만 보이는 별도 작업이다. 확인 문구는 SQLite에만 남아 있고 동기화
파일로 기록되지 않은 Notes가 사라질 수 있음을 명시한다. 이 작업은 활성 Notes
세션을 요구하지 않는 Tauri 명령으로 실행하여, 구형 DB 때문에 작업공간을 열지
못한 상태에서도 사용할 수 있게 한다.

초기화 순서는 다음과 같다.

1. 가능한 경우 진행 중인 편집과 파일 동기화를 정리하고 새 작업을 막는다.
2. Notes 동기화 파일과 첨부파일을 보존한다.
3. app-local SQLite 세트와 구형 vault-local SQLite 세트를 제거한다.
4. 현재 스키마로 새 DB를 생성한다.
5. 유효한 Notes 동기화 파일을 가져온다.
6. 가져온 topic이 없으면 기본 안내 노트 세트를 유지하고 동기화 파일로 내보낸다.
7. 작업공간을 다시 열어 결과를 표시한다.

### 전체 Notes 데이터 삭제

기존 설정 작업과 확인 단계를 유지하되, 파일 단일 진실 공급원 구조에 맞게 삭제
범위를 정확히 표시한다. Notes 동기화 파일을 남기면 다시 가져와져 전체 삭제가
무효화되므로 Yonalist가 소유한 topic 및 trash 파일도 함께 삭제한다.

삭제 순서는 다음과 같다.

1. 진행 중인 편집과 파일 동기화를 정리하고 새 작업을 막는다.
2. app-local 및 구형 vault-local Notes SQLite 세트를 제거한다.
3. Yonalist가 소유한 Notes topic/trash Markdown 파일과 첨부파일을 제거한다.
4. 사용자 일반 Markdown 파일과 앱 설정은 보존한다.
5. 현재 스키마 DB를 새로 만들고 기본 안내 노트 세트를 생성한다.
6. 안내 노트를 동기화 파일로 내보내고 작업공간을 다시 연다.

## 안내 노트 불변 조건

초기 시작, DB 초기화, 전체 삭제가 모두 동일한 규칙을 사용한다.

- 가져올 수 있는 활성 topic 파일이 하나 이상이면 파일 내용이 기준이며 안내
  노트 잔여물은 제거한다.
- 가져올 수 있는 활성 topic 파일이 없으면 기본 안내 노트 세트를 정확히 한 번
  생성한다.
- 잘못된 형식의 파일은 기존 격리·오류 처리 규칙을 따르며 유효한 topic으로 세지
  않는다.
- 기본 안내 노트의 현재 문구와 계층은 변경하지 않는다.

## 경계와 책임

- React 설정 UI는 두 작업의 목적과 삭제 범위를 구분하고 성공 후 재로딩을
  요청한다.
- 프론트엔드 Notes 서비스는 DB 초기화용 세션 비의존 IPC와 전체 삭제 IPC를 각각
  노출한다.
- Rust/Tauri 계층은 vault 경로를 검증하고 기존 저장소 삭제 직렬화 장치를
  재사용한다.
- 저장소 계층은 현재 스키마 생성과 안내 노트 seed를 담당한다.
- 파일 동기화 계층은 유효한 파일 import 결과에 따라 안내 노트 유지 여부를
  결정한다.

## 실패 처리

- 삭제·초기화 중에는 같은 vault에 대한 동시 Notes 작업을 허용하지 않는다.
- 경로 검증에 실패하면 어떤 파일도 삭제하지 않고 오류를 반환한다.
- Notes 소유 경계를 판별할 수 없는 파일은 삭제하지 않는다.
- 일부 단계가 실패하면 오류를 표시하고 성공으로 재로딩하지 않는다. 남은 상태는
  다음 실행에서 기존 bootstrap 규칙으로 복구 가능해야 한다.
- 구형 DB가 발견되더라도 자동 마이그레이션이나 자동 삭제는 하지 않는다.

## 비대상

- v1 또는 다른 구형 Notes 스키마의 데이터 마이그레이션
- 구형 DB에서 동기화되지 않은 노트를 자동 추출하는 복구 도구
- 기본 안내 노트 내용이나 디자인 변경
- Notes 외 Inbox, 캐시, outbox, 앱 전체 설정의 초기화
- 사용자가 직접 만든 일반 vault 파일 삭제

## 검증

### Rust·파일시스템

- 구형 vault-local DB만 존재하고 작업공간 초기화가 실패한 상태에서 DB 초기화가
  성공하는지 확인한다.
- DB 초기화가 동기화 Markdown 파일과 첨부파일을 보존하는지 확인한다.
- 동기화 topic이 있는 초기화는 해당 노트를 가져오고 안내 노트를 남기지 않는지
  확인한다.
- 동기화 topic이 없는 초기화는 안내 노트 일곱 개 노드를 정확히 생성하는지
  확인한다.
- 전체 삭제가 Notes 소유 topic/trash/attachment와 두 SQLite 위치를 제거하되 일반
  vault 파일을 보존하는지 확인한다.
- 전체 삭제 직후 안내 노트가 DB와 동기화 파일에 생성되는지 확인한다.

### 프론트엔드

- 개발 환경에만 DB 초기화가 표시되고 전체 삭제는 계속 표시되는지 확인한다.
- 두 확인 창이 서로 다른 삭제 범위를 정확히 안내하는지 확인한다.
- 초기 세션이 없어도 DB 초기화 요청을 보낼 수 있는지 확인한다.
- 성공 후 Notes 작업공간이 다시 열리고 새 상태를 표시하는지 확인한다.

### 데스크톱

격리된 임시 vault에서 구형 DB 오류를 재현한 뒤 DB 초기화로 앱을 복구한다. 이어서
동기화 파일 보존 경로와 전체 삭제 후 안내 노트 재생성 경로를 각각 한 번 확인한다.
최종 단계에서 관련 집중 테스트, owning suite, lint/build, Rust 테스트, 포맷 및
`git diff --check`를 실행한다.
