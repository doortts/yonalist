# Workflowy식 계층 선택·키보드 이동·노트 툴바 정렬 설계

## 계약

| 항목 | 내용 |
| --- | --- |
| 목표 | 선택한 블릿을 Workflowy 단축키로 이동하고, 선택한 부모의 하위 블릿을 같은 선택 단위로 취급하며, 노트 화면의 전체화면 아이콘을 다른 툴바 아이콘과 정렬한다. |
| 완료 조건 | Windows/Linux `Alt+Shift+↑/↓`, macOS `Ctrl+Shift+↑/↓`가 선택된 한 개 이상의 블릿을 한 단계 이동한다. 부모가 선택 범위에 들어오면 보이는 모든 자손도 선택 표시·집계·드래그 원본에 포함된다. 이동 저장은 구조 루트만 한 번의 배치 호출로 처리한다. 노트 화면 전체화면 버튼의 중심선이 48px 노트 툴바 중심선과 일치한다. |
| 비대상 | Workflowy의 모든 단축키 재현, 선택 모델 전면 교체, 새 상태 관리 계층, Rust/IPC/SQLite 형식 변경, 모바일 레이아웃 변경은 포함하지 않는다. |
| 경계 | React 선택 투영, 키보드 해석, 기존 선택 명령 라우터, 기존 배치 이동, App/TitleBar CSS만 변경한다. |
| 직접 확인 | Tauri 앱을 새로 빌드·실행해 부모와 자손 선택, 위/아래 이동, 접힌 자손 보존, 아이콘 수직 정렬을 확인한다. |

## 확인된 원인

1. `resolveOutlineKey`의 선택 이동 키가 일반 플랫폼에서 `Ctrl`, macOS에서 `Cmd`를 사용한다. Workflowy 공식 Move Items 키인 일반 플랫폼 `Alt`, macOS `Ctrl`과 다르다.
2. `selectionRangeIds`는 앵커와 헤드 사이의 평면적인 보이는 행만 반환한다. 선택된 부모 아래의 자손을 선택 폐포에 추가하지 않는다.
3. 전체화면 버튼은 높이 42px인 고정 제목줄에 수직 정렬되고, 노트 메뉴 버튼은 상단 여백 뒤의 높이 48px 툴바에 정렬된다. 현재 중심선 차이는 `8px pane top + 4px content gap + 24px toolbar center - 21px titlebar center = 15px`이다.

## 선택한 설계

### 1. 보이는 선택을 하위 트리 폐포로 확장

기존 `NotesSelection`의 앵커·헤드·명시 ID 모델은 유지한다. 별도의 상태를 추가하지 않고, 선택을 화면 행으로 물질화할 때 선택된 각 행의 보이는 자손을 추가하는 순수 함수를 둔다.

함수는 다음 입력을 사용한다.

- 기존 `selectionRangeIds` 결과
- 현재 `visibleNodeIds`
- `NormalizedNotesWorkspace.childIdsByParent`
- 각 노드의 `isCollapsed`

선택된 행을 루트로 깊이 우선 순회하되, 접힌 노드 아래는 화면에 보이지 않으므로 순회를 멈춘다. 중첩 선택은 `Set`으로 한 번만 방문한다. 결과는 다시 `visibleNodeIds` 순서로 반환한다.

이 결과를 다음 모든 소비자에 동일하게 사용한다.

- 행의 `data-range-selected` 표시
- 선택 툴바 개수
- 선택 명령 자격 계산
- 선택 드래그 원본과 미리보기
- 선택 권한 준비와 클립보드 준비

구조 변경 명령은 기존 `structuralRootIds` 정규화를 그대로 사용한다. 따라서 부모와 자손이 모두 보이는 선택에 포함돼도 서버에는 부모 루트만 전달되며, 숨겨진 자손도 트리 구조상 함께 이동한다.

### 2. Workflowy 이동 키 매핑

선택이 살아 있을 때 다음 키만 `moveUp`/`moveDown` 선택 명령으로 라우팅한다.

| 플랫폼 | 위로 | 아래로 |
| --- | --- | --- |
| Windows/Linux | `Alt+Shift+↑` | `Alt+Shift+↓` |
| macOS | `Ctrl+Shift+↑` | `Ctrl+Shift+↓` |

IME 조합 중, `Process` 키, 자동 반복은 기존처럼 실행하지 않는다. 잘못된 플랫폼 키인 일반 플랫폼 `Ctrl+Shift+↑/↓`와 macOS `Cmd+Shift+↑/↓`는 이동을 실행하지 않는다.

선택 표시가 없는 일반 커서 행도 같은 키로 이동할 수 있게 한다. 이 경우 기존 단일 `moveNode` 경로를 사용하고 같은 부모의 직전/다음 형제와 위치만 교환한다. 부모를 이동하면 저장소의 기존 트리 이동 계약에 의해 모든 자손이 함께 이동한다. 필터 화면처럼 완전한 형제 순서를 보장할 수 없는 투영에서는 잘못된 순서를 계산하지 않고 선택 명령 경로를 사용하도록 제한한다.

공식 참고:

- <https://workflowy.com/help/hotkeys>
- <https://workflowy.com/help/bullets>

### 3. 전체화면 아이콘 정렬

`app-shell`에 현재 기능 ID를 데이터 속성으로 노출한다. 노트 기능이 활성화됐을 때만 `detail-end` 버튼 그룹의 높이와 위쪽 위치를 노트 툴바와 같은 좌표계로 맞춘다.

- `top = var(--pane-top) + var(--content-titlebar-gap) = 12px`
- `height = 48px`
- 중심선 = `12px + 24px = 36px`

다른 기능의 제목줄 배치는 바꾸지 않는다. JavaScript 위치 측정, ResizeObserver, 포털은 추가하지 않는다.

## 검토한 대안

### 선택 상태에 모든 자손 ID 저장

선택 표시 계산은 단순해지지만 접기·필터·이동 뒤 ID 집합이 오래될 수 있고, 선택 변경마다 큰 배열을 복제한다. 현재 앵커/헤드 모델을 불필요하게 교체하므로 제외한다.

### CSS로 선택된 부모의 뒤쪽 행만 강조

화면은 비슷해 보여도 툴바 개수, 드래그 원본, 복사·삭제·이동 대상이 달라진다. 동작 계약을 만족하지 못하므로 제외한다.

### 전체화면 버튼을 NotesOutlinePane으로 이동

시각적으로 직접 정렬할 수 있지만 안정적인 Notes pane에 App 레이아웃 상태와 콜백을 새로 전달해야 한다. 기능 경계를 넓히고 메모 안정성을 떨어뜨리므로 CSS 상태 규칙을 선택한다.

## 수치 기반 성능 예산

- 선택 폐포 계산 시간: `O(V + E_s)`. `V`는 보이는 행 수, `E_s`는 선택된 보이는 하위 트리의 자식 연결 수다.
- 방문 상한: 보이는 ID 필터 1회, 선택된 각 노드와 자식 연결 최대 1회.
- 추가 메모리: 보이는 행 ID 최대 `V`개인 `Set` 하나와 순회 스택 하나.
- 렌더링: 기존 행 메모를 유지하며 `isSelected` 값이 바뀐 행만 실제 행 렌더 결과가 바뀐다.
- 저장 호출: 선택 크기와 무관하게 이동 한 번당 배치 저장 1회. 단일 커서 행은 단일 이동 저장 1회.
- 전체화면 정렬: CSS 선언만 추가하므로 이벤트 리스너·측정·React 상태·리렌더 추가 0개.
- 기준선: 관련 단위 테스트 202개가 979ms에 통과했고, 격리 작업 공간 전체 테스트 3,852개가 실패 없이 통과했다.

## TDD 검증 순서

1. 선택 폐포 단위 테스트를 실패시킨다: 부모 단독, 중첩 범위, 접힌 부모, 순서 보존.
2. 워크스페이스 통합 테스트를 실패시킨다: 마우스와 `Shift+화살표` 선택이 자손을 모두 표시하고 이동 시 구조 루트 한 개만 배치 호출한다.
3. 키보드 테스트를 실패시킨다: 플랫폼별 올바른 키, 잘못된 키, IME/반복, 단일 커서 행과 다중 선택.
4. App/CSS 테스트를 실패시킨다: notes 기능 속성과 12px/48px 정렬 규칙.
5. 각 실패마다 최소 구현 후 소유 테스트만 통과시킨다.
6. 새 Tauri 프로세스에서 사용자 경로를 확인한 뒤 프론트엔드 최종 게이트를 한 번 실행한다.
