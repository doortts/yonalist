# Notes RemoveTopic 멱등성 보강 설계

## 목표

파일로 한 번도 내보내지지 않은 새 루트 블릿을 다른 루트 아래로 이동해도 Notes 동기화가 오류 없이 현재 부모 토픽만 내보내야 한다. 이미 남아 있는 메타데이터 없는 `RemoveTopic` 표식도 자동으로 정리되어야 한다.

## 확인된 원인

Notes는 SQLite 변경을 즉시 외부 파일로 쓰지 않고 마지막 변경 후 3초 동안 모아 내보낸다. 새 루트가 이 기간 안에 다른 루트 아래로 이동하면 독립 Markdown 파일과 `sync_topics` 행이 아직 없을 수 있다.

로컬 이동 경로는 이전 루트가 실제로 파일을 소유했는지 확인하지 않고 `__yonalist_remove_topic__:<topic-id>` 표식을 생성한다. 반면 삭제 실행 경로는 해당 `sync_topics` 행이 반드시 존재한다고 가정하므로 `Query returned no rows`로 실패하며 표식이 남는다.

## 선택한 접근

생성부와 실행부를 함께 보강한다.

1. 로컬 이동 시 이전 루트의 `sync_topics` 행이 있을 때만 `RemoveTopic` 표식을 만든다. 메타데이터가 없다면 삭제할 파일도 없으므로 표식을 만들지 않는다.
2. 실행 시점에 메타데이터가 사라진 기존 고아 표식을 발견하면, 현재 부모 토픽 또는 휴지통이 최신 상태로 내보내졌는지 먼저 확인한 뒤 파일 삭제가 이미 완료된 것으로 간주하고 표식만 정리한다.
3. 실제 메타데이터와 파일이 있는 기존 루트 이동은 지금처럼 새 소유자 파일의 내구성을 먼저 확인한 뒤 이전 파일을 삭제한다.

생성부만 고치면 기존 사용자 DB의 고아 표식이 복구되지 않고, 실행부만 고치면 불필요한 삭제 작업이 계속 만들어진다. 두 경계를 함께 보강하는 것이 최소한의 완결된 해결이다.

## 데이터 흐름

### 최초 내보내기 전 이동

1. 새 루트 생성으로 일반 dirty 표식이 생긴다.
2. 다른 루트 아래로 이동한다.
3. 이전 루트의 `sync_topics` 행이 없으므로 `RemoveTopic`은 만들지 않는다.
4. 노드 변경 dirty 표식은 현재 부모 토픽으로 해석되어 부모 파일을 내보낸다.

### 기존 고아 표식 복구

1. `RemoveTopic`이 참조하는 노드의 현재 소유 토픽 또는 휴지통을 확인한다.
2. 새 소유 대상이 SQLite 상태와 동일하게 파일로 내보내졌는지 검증한다.
3. 삭제 대상 `sync_topics` 행이 없으면 파일 제거 없이 dirty 표식만 원자적으로 지운다.

### 이미 내보낸 루트 이동

기존 `sync_topics` 행과 파일을 사용해 현재 동작대로 이전 파일을 안전하게 삭제하고 표식을 지운다.

## 오류 처리와 안전성

- 현재 부모 또는 휴지통이 최신 파일 상태가 아니면 고아 표식을 지우지 않는다.
- 메타데이터가 있는 파일은 기존 해시·격리 검증을 그대로 통과해야 삭제한다.
- 사용자 노드, 첨부파일, 휴지통 데이터는 삭제하지 않는다.
- 내보내기 디바운스 3초는 성능과 클라우드 이벤트 병합을 위해 유지한다.

## 검증

- 최초 내보내기 전 루트 이동이 `RemoveTopic`을 만들지 않고 부모 파일만 내보낸다.
- 메타데이터 없는 기존 `RemoveTopic`이 오류 없이 정리된다.
- 메타데이터와 파일이 있는 루트 이동은 이전 파일을 계속 삭제한다.
- 관련 Rust 모듈 테스트와 전체 Rust 테스트, 포맷 및 diff 검사를 통과한다.

## 비대상

- IME 조합 중 초안 저장 정책 변경
- 내보내기 디바운스 시간 변경
- Notes 파일 형식 또는 SQLite 스키마 변경
- 사용자의 현재 Notes DB를 직접 수정하는 작업
