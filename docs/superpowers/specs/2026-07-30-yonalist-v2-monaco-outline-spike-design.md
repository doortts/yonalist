# Yonalist v2 Monaco Outline Spike Design

**Date:** 2026-07-30

**Status:** Approved for experimental implementation

## Goal

Determine whether replacing the complete visible bullet page with one Monaco
Editor produces native-editor Enter, Backspace, caret, and large-outline
performance while preserving Yonalist's current shell, storage, command, and
visual contracts.

## Observable Contract

- `?outline=monaco` replaces the complete visible bullet list in each pane
  with one Monaco editor. The existing React outline remains available without
  that query parameter as the A/B control.
- One visible text node maps to one Monaco model line. Node identity remains
  separate from line number and survives insertions, removals, and moves.
- Normal title typing updates the Monaco model immediately and publishes only
  the affected Yonalist node draft.
- Enter splits the current node through `NotesStore.beginSplitNode`, places the
  new caret synchronously, and keeps accepting native repeated keydown events
  while earlier commits are pending.
- Backspace inside text remains a Monaco text edit. Backspace at the beginning
  merges with the previous eligible bullet; an empty bullet is removed through
  the existing optimistic store commands.
- Tab and Shift+Tab route through the existing Yonalist indent and outdent
  commands. Arrow keys and wrapped-line caret movement remain Monaco-owned.
- Ctrl/Cmd+Z and Ctrl/Cmd+Shift+Z route to the existing application interaction
  history; Monaco does not become a second Undo authority.
- Two split panes create independent editor views. When they show the same
  projection, store patches keep their models consistent without moving focus
  between panes.
- The resting text, font, width, line height, background, indentation, and
  bullet geometry match the current v2 layout closely enough for direct visual
  comparison. No new design is introduced.

## Non-goals

- The spike does not replace Rust, SQLite, IPC contracts, viewport queries,
  optimistic receipts, or session history.
- Image editing, image resizing, menus, pointer multi-selection, and
  cross-pane drag/drop remain on the React control surface. Image lines are
  represented as non-editable experimental placeholders rather than claiming
  feature parity.
- The spike does not use Monaco private DOM structure or private VS Code
  services. Only the public `monaco-editor` API and public CSS entry are used.
- The spike does not claim production readiness from unit tests. A fresh
  browser runtime and measured A/B results are required.
- The current React outline is not deleted.

## Boundaries

The changed boundary is frontend-only:

- React chooses the experimental outline surface and owns surrounding controls.
- A pure projection maps visible `NoteView` objects to Monaco lines.
- A Monaco adapter owns editor/model lifecycle and translates edits into
  existing `NotesStore` operations.
- Rust, SQLite, generated contracts, and native configuration are unchanged.

## Architecture

### Surface selection

`NotesOutline` retains the current header, selection, image-ingest, and
navigation ownership. Its row-body region chooses between:

- the current ordered React row list; and
- a lazy `MonacoOutlineSurface` when `outline=monaco` is present.

Keeping both surfaces in the same build gives a fair runtime A/B comparison
against identical data and shell code. Monaco is dynamically imported so the
control path and initial production graph remain measurable.

### Projection

`monacoOutlineProjection.ts` is framework-independent. It produces:

```ts
interface MonacoOutlineLine {
  readonly nodeId: string;
  readonly text: string;
  readonly depth: number;
  readonly editable: boolean;
}

interface MonacoOutlineProjection {
  readonly lines: readonly MonacoOutlineLine[];
  readonly value: string;
  readonly lineByNodeId: ReadonlyMap<string, number>;
}
```

Line numbers are one-based. Text nodes use their current draft title. Image
nodes use a stable display label and are marked non-editable. A differential
planner computes the smallest contiguous replacement between two projections.
The editor applies that replacement with `executeEdits` while suppressing the
draft callback generated by its own reconciliation.

### Edit ownership

Monaco owns the immediate text buffer, caret, wrapping, composition, and
scrolling. Yonalist remains the domain authority:

1. A same-line Monaco edit calls `store.setDraft(nodeId, lineText)`.
2. Enter and boundary Backspace are prevented before Monaco changes line
   structure.
3. The existing optimistic store operation updates the authoritative frontend
   projection synchronously.
4. The Monaco adapter reconciles that projection and restores the caret by
   node ID, not stale line number.
5. The existing asynchronous command receipt confirms or rolls back the
   optimistic state.

Composition events never trigger structural commands. A composition result is
persisted as an ordinary same-line draft after Monaco finishes composing.

### Undo

Monaco's Ctrl/Cmd+Z keybindings are overridden. They call the same
`NotesInteractionHistory` callbacks used by the rest of the app. Model
reconciliation edits are adapter-owned and never create a second product
history contract.

### Styling

The editor disables code-specific chrome: line numbers, minimap, overview
ruler, folding controls, current-line highlight, suggestions, bracket
features, and extra scrolling. Public editor options set the current Yonalist
font, line height, wrapping, padding, and cursor behavior. Public model
decorations provide bullet and indentation classes. CSS is scoped beneath
`.notes-monaco-outline` and does not modify private Monaco selectors except the
documented host classes necessary to remove the default background.

## Manual Proof

Use a freshly started preview and the same data in two tabs:

1. Open the control surface without a query parameter.
2. Open `?outline=monaco` for the experimental surface.
3. In each, hold Enter for 20 generated bullets, hold Backspace to remove them,
   and verify the final caret and order.
4. Type Korean IME text, split it at the start, middle, and end, then Undo and
   Redo.
5. Open and resize a split pane; repeat Enter in the secondary pane and verify
   its focus remains local.
6. Load the fixed large-outline fixture and compare keydown-to-paint,
   dropped-frame, memory, scroll, cold-editable, and gzip bundle measurements.

## Decision Gate

The spike may replace the React outline only after a separate parity project
implements images, selection, drag/drop, menus, supporting notes, accessibility
list semantics, and golden-image parity. This spike succeeds when it produces
honest performance evidence and a working text-outline vertical slice; it does
not succeed by hiding missing features.
