# 블릿 메뉴 화면 경계 처리 설계

## 목표

블릿 메뉴를 어느 위치에서 열더라도 팝업 전체가 현재 앱 화면 경계 안에 유지되고, 공간이 부족하면 메뉴 내부 스크롤로 모든 명령에 접근할 수 있어야 한다.

## 원인

`NotesBulletMenu`는 Base UI의 `Menu.Positioner`를 사용한다. Positioner는 트리거 위치와 충돌 여백을 계산해 현재 배치 방향에서 실제로 사용할 수 있는 높이를 `--available-height` CSS 변수로 제공한다.

현재 `.notes-bullet-menu`는 이 값을 사용하지 않고 `min(520px, calc(100vh - 16px))`로 높이를 제한한다. 이 식은 전체 뷰포트 높이만 알고 트리거 위·아래의 실제 공간은 알지 못한다. 따라서 화면 아래쪽 트리거에서 메뉴가 위로 전환될 때 팝업이 사용 가능한 상단 공간보다 커질 수 있고, 결과적으로 메뉴 상단이 화면 밖으로 밀려 잘린다.

저장소의 공통 Select 팝업은 같은 Base UI 위치 계산값을 `max-height: min(18rem, var(--available-height))`로 사용하고 있으며 이 동작이 기준 구현이다.

## 해결 방식

`.notes-bullet-menu`의 최대 높이를 다음 규칙으로 변경한다.

```css
max-height: min(520px, var(--available-height));
```

- `520px` 상한은 유지해 큰 화면에서 메뉴가 지나치게 길어지지 않게 한다.
- 트리거 위치에 따라 Base UI가 계산한 실제 높이를 사용한다.
- 공간이 부족하면 기존 `overflow-y: auto`가 메뉴 내부 스크롤을 제공한다.
- 메뉴의 232px 기본 폭, 단축키가 있는 화면의 260px 폭, 명령 구성과 키보드 동작은 변경하지 않는다.

고정된 더 작은 높이를 사용하는 방식은 큰 화면의 공간을 낭비하고 작은 창에서 다시 실패할 수 있어 제외한다. Positioner의 배치 전략을 바꾸는 방식도 팝업 자체가 가용 공간보다 큰 문제를 직접 해결하지 않으므로 제외한다.

## 완료 조건

| 조건 | 확인 방법 |
| --- | --- |
| 화면 아래쪽 블릿에서 메뉴를 열어도 상단과 하단이 잘리지 않는다 | 높이를 줄인 격리 Tauri 앱에서 하단 블릿 메뉴 열기 |
| 공간보다 긴 메뉴는 내부 스크롤로 모든 명령에 접근할 수 있다 | 메뉴의 계산 높이와 스크롤 가능 상태 확인 |
| 단축키 표시와 메뉴 폭이 유지된다 | 기존 `NotesBulletMenu` 테스트와 실제 메뉴 확인 |
| 보관함·휴지통·내보내기 등 작은 메뉴 동작이 유지된다 | 기존 메뉴 테스트 실행 |

## 영향 범위와 비대상

- 영향 범위: Notes 프런트엔드 CSS와 해당 회귀 테스트
- 비대상: 메뉴 명령, 단축키 매핑, React 상태, IPC, Rust, SQLite, Undo/Redo

## 테스트 전략

1. `NotesBulletMenu` CSS 계약 테스트에 `--available-height` 사용을 요구하고 기존 구현에서 실패하는지 확인한다.
2. CSS를 최소 변경한 뒤 해당 테스트와 메뉴 소유 테스트를 통과시킨다.
3. 새 포트와 별도 데이터 경로를 사용하는 Tauri 앱에서 창 높이를 줄이고 화면 아래쪽 블릿 메뉴를 열어 직접 확인한다.
4. 변경 범위가 프런트엔드뿐이므로 최종적으로 `npm test`, `npm run lint`, `npm run build`, `git diff --check`를 실행한다. Rust·IPC·저장소 경계는 변경하지 않으므로 Cargo 검증은 제외한다.
