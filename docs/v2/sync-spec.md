# Notes 파일 SSOT 동기화 스펙 — 포맷 v1

2026-08-18 · 기준 코드 `feat/readable-frontmatter-time@8e2fae26` · [구현 계획](../superpowers/plans/2026-08-15-notes-sync-port-implementation-plan.md) M0.1의 산출물

## 1. 지위와 목표

- 이 문서가 M1–M6 구현의 진실 소스다. 마일스톤·항목·게이트는 구현 계획이, 테스트 이름·경로는 [테스트 설계](../superpowers/plans/2026-08-15-notes-sync-port-test-design.md)가 소유한다. 여기서는 그 둘이 잠그는 **계약**만 적는다.
- 문법(§4~§5)은 이 절만 읽고 렌더러와 파서를 바이트 단위로 재작성할 수 있게 쓴다.
- 문법의 진실 소스는 `crates/notes-sync`의 `render.rs`와 `parse.rs`다. 이식이 끝나 v1 코드는 이 저장소에 없고, **v1 파일을 읽는 호환도 목표가 아니다**(결정 6 취소).

**목표 한 줄.** vault 폴더를 markdown 서버에 얹으면 사람이 문서를 찾아 열고 이미지까지 볼 수 있다. 앱의 기능이 거기서 동작할 필요는 없다.

**저장의 경계.** vault는 읽을거리를 진다 — 본문·노트·계층·순서·체크·별표·접힘·첨부 바이트·삭제된 노드, 그리고 정체성인 `yid`와 `t`. DB는 살림살이를 진다 — 충돌 로그, 방출 추적, HLC 클록, 검색 색인, 첨부 위치와 미참조 시각, UI 상태. DB를 잃어도 문서 내용은 vault에서 그대로 돌아온다.

### 3.1 폴더 이름

페이지 노드 하나가 폴더 하나다. 이름은 `<정제한 제목>-<블록 id>`이고 **접미사는 조건 없이 언제나 붙는다**. 겹칠 때만 붙이면 "누가 먼저였나"를 따지는 비교가 필요하고, 그 비교는 두 기기가 서로를 모르는 동안 다른 답을 낸다.

정제는 순서대로:

1. NFC 정규화, 제어문자와 줄바꿈 제거.
2. `/ \ : * ? " < > |`, `# % { } ^ ~ [ ] ( )`, 연속 공백을 `-`로. 괄호까지 치우는 이유: 이 이름들이 markdown 링크 대상에 그대로 들어가는데 `)`가 링크를 닫아 버린다. 정제가 URL-위험 문자를 전부 없애므로 링크 대상은 percent 인코딩 없이 원문 그대로 쓴다.
3. 연속 `-`를 하나로, 앞뒤 `-`와 `.` 제거. 선두 `.`은 폴더를 숨기므로 반드시 제거한다.
4. 40자 **동시에** UTF-8 120바이트로 절단. 자소 경계에서 자르고 이모지를 쪼개지 않는다.
5. `CON` `PRN` `AUX` `NUL` `COM1`–`COM9` `LPT1`–`LPT9`(대소문자 무관)이면 앞에 `_`.
6. 남은 것이 없으면 `untitled`.
7. `-<접미사>`를 붙인다. 접미사는 **그 페이지의 블록 id 전체**다 — `yid`가 이미 12자라 잘라 낼 것이 없다([layout.rs:38-43](../../crates/notes-sync/src/layout.rs#L38)). 폴더 이름만 보고 어느 문서인지 알 수 있다. 대소문자만 다른 두 id는 두 폴더를 받는다. 절단은 이 단계 **전** 값에 적용한다. home의 리터럴 `root`는 이 함수가 거절한다 — home에는 자기 폴더가 없다(§3.2).

전체 길이는 최대 53자·133바이트다. 제목이 바뀌어도 폴더 이름은 따라가지 않는다 — 자동 rename은 동기화가 가장 못 다루는 연산이다. 사용자가 실행하는 "vault 이름 정리"가 폴더를 제목에 맞춘다.

### 3.2 문서 파일

폴더의 문서는 언제나 `README.md`다. home 문서는 vault 루트의 `README.md`이고 폴더 접미사가 없다.

**home 문서는 페이지들의 색인이다.** 페이지는 전부 home의 분할 문서(§4.5)이므로, home의 노드 라인은 페이지마다 하나씩 나오는 split 링크 줄이 전부다. 페이지 순서가 곧 줄 순서다. home은 페이지를 만들거나 지우거나 제목·순서를 바꿀 때마다 다시 쓰이는 **가장 뜨거운 파일**이다 — 타이핑은 건드리지 않고, 노드 단위 병합과 디바운스가 이 집중을 흡수한다. 알고 지불하는 비용이다.

### 3.3 첨부 배치

| 참조 수 | 바이트가 있는 곳 | 문서에서 가리키는 법 |
|---|---|---|
| 1 | 그 페이지 폴더의 `assets/` | `assets/<이름>` |
| 2 이상 | vault 루트의 `assets/` | 깊이만큼 `../` |
| 0 | 있던 자리에 그대로 — 최대 2주 | 가리키는 문서가 없다 |

파일 이름은 두 자리에서 같다: `<원래이름>-<내용 해시 앞 12자>.<확장자>`. **원래 이름은 확장자를 뗀 basename**을 §3.1의 1–4단계로 정제한 것이고, **확장자는 원본명이 아니라 디코딩된 MIME에서** 소문자로 정한다 ([image_assets.rs:45-46](../../crates/notes-sqlite/src/image_assets.rs#L45)의 `format_details` 그대로 — 선언과 실제가 다른 파일이 못 들어온다). 이동은 폴더만 달라지는 일이 된다.

- 붙일 때 바이트를 해시해 같은 해시가 이미 있으면 파일을 쓰지 않고 그것을 가리킨다. 사용자가 다른 이름으로 올렸어도 디스크 이름은 먼저 들어온 것을 유지하고, **블릿이 쓴 이름은 DB가 노드마다 따로 기억한다**.
- 참조가 1→2가 되면 루트로 올리고, 2→1이 되면 남은 페이지 폴더로 내린다. 순서는 언제나 **쓰고 나서 지운다** — 전파가 끊겨도 두 곳에 있는 상태로 끝나지 사라지지 않는다. 내용이 같으므로 잠시 둘인 것은 무해하다.
- 참조는 **살아 있는 노드와 휴지통의 노드**를 함께 센다. 참조 0이면 그 자리에 두고 시각만 기록한다. 삭제는 사용자가 첨부 목록에서 누른다.
- 승격할 때 참조들이 서로 다른 디스크 이름을 들고 있으면(두 페이지가 같은 바이트를 각자 이름으로 넣었다) 루트의 이름은 **정제된 이름의 바이트 오름차순 최소**를 쓴다 — 어느 기기가 계산해도 같은 답이 나온다.
- **휴지통에 들어간 이미지의 바이트는 루트 저장소로 승격한다.** `trash.md`는 `.yonalist/` 안이라 페이지 폴더의 첨부를 합법으로 가리킬 수 없다(§3.4) — trash의 이미지 라인은 언제나 `../assets/…`다.

### 3.4 링크 규칙

첨부 링크는 **그 문서가 있는 폴더 기준 상대 경로**다. 절대 경로도, vault 루트 기준 경로도 쓰지 않는다.

검증은 모양이 아니라 **해석 결과**로 한다: 링크를 문서 위치에서 resolve한 경로가 **루트 `assets/` 또는 그 문서가 속한 페이지의 `assets/`** 안에 떨어지면 합법이고, 그 밖은 전부 격리다. 분할 문서는 페이지보다 한 겹 깊으므로 같은 페이지 첨부가 `../assets/…`로, 루트 첨부가 `../../assets/…`로 나온다 — 문서가 자기 깊이를 아니 렌더도 검증도 결정적이다.

**파일 접근 안전 계약**: vault의 모든 읽기·쓰기는 심볼릭 링크를 따라가지 않고(no-follow), 일반 파일임을 확인하고, 임시 파일은 대상과 같은 디렉터리에 만든다. resolve한 경로가 vault 밖이면 중간 디렉터리가 링크였다는 뜻이므로 거부한다. 문자열 검사(`../` 개수)만으로는 링크를 못 막는다 — v1 file_io의 guarded read·no-replace 이동 계약(M1.3)이 이 조항의 구현이다.

### 3.5 문서 수명

페이지 노드가 휴지통에 들어가거나 더는 root의 직계 자식이 아니게 되면 exporter가 그 폴더를 정리한다. 순서가 안전을 만든다:

1. 그 폴더 `assets/`에서 **참조가 살아 있는 첨부(휴지통 참조 포함)를 루트 저장소로 승격**한다 — 쓰고 나서 지운다.
2. 승격이 끝난 뒤에 `README.md`와 폴더를 지운다.

이 순서가 없으면 폴더 정리가 휴지통이 아직 가리키는 바이트를 지워, 다른 기기에서 복구한 노드의 이미지가 사라진다. 분할 문서의 폴더도 같은 규칙을 탄다.

## 4. 문서 문법

### 4.1 공통 규칙

- 인코딩 UTF-8, 개행 LF. 파서는 CRLF·CR을 LF로 정규화한다.
- **HLC**: 21자 고정폭 `mmmmmmmmm-cc-dddddddd` — millis base36 소문자 9자 zero-pad, counter base36 2자, device 소문자 hex 8자. decode는 재인코딩 일치까지 요구한다(비정규형 거부, [hlc.rs:73-95](../../crates/notes-sync/src/hlc.rs#L73)). 빈 문자열은 "없음"이고 사전순 비교에서 언제나 진다. 발급 규칙: `now()`는 `millis = max(벽시계, 직전.millis)`, 같은 millis면 counter 증가 — 벽시계 역행에도 단조롭다. `observe(원격)`은 직전을 원격 최댓값 이상으로 끌어올려 병합 후 발급분이 항상 원격을 이기게 한다. **counter가 1,296을 넘으면 millis를 1 올리고 counter를 0으로** — 대량 붙여넣기가 한 트랜잭션에서 수천 노드를 스탬프하면 한 밀리초 안에서 실제로 넘친다. **클록은 영속하지 않는다** — 부팅 때 `max(notes_nodes.hlc) ∪ max(sync_documents.applied_max_hlc)`를 observe해서 재시드한다. 파생 상태라 크래시로 잃어도 되고, 저장된 클록이 실제 행보다 뒤처지는 역행 버그가 원리적으로 없다.
- **기기 id (스탬프의 device 8자)**: 데이터베이스를 처음 열 때 한 번 정하고 다시 바꾸지 않는다([worker.rs](../../crates/notes-sqlite/src/worker.rs), `sync_meta.device_id`). 값은 **기계에서 유도한다** — `gethostuuid(2)`가 주는 16바이트(`IOPlatformUUID`와 같은 값)를 sha256으로 줄여 앞 4바이트를 hex로 적는다([hlc.rs](../../crates/notes-sync/src/hlc.rs), `device_seed`). vault는 데이터베이스보다 오래 산다. 같은 맥에서 데이터베이스를 다시 만들 때마다 새 기기가 되면 폴더에 남은 옛 세대 스탬프와 자기 자신이 싸운다. 이 맥의 `IOPlatformUUID`는 UUID version 5라서 지우고 재설치해도 같은 값이 나오고, App Sandbox와 hardened runtime 아래에서도 읽힌다(entitlement 불필요). 하드웨어 식별자 자체는 이 함수 밖으로 나가지 않는다 — 8자는 vault의 모든 파일에 실리고 vault는 공유 폴더에 놓이는 것이다.

  **유도에 실패하면 랜덤값을 만들지 않고 provisioning이 실패한다.** 랜덤 id는 앱이 계속 도는 것처럼 보이게 하지만, 아무도 모르는 기기로서 vault에 스탬프를 찍고 그 정체를 다음 재설치에 버린다. 앱을 지웠다 다시 깔는 것은 사람이 하는 일이다.

  **8자인 이유는 `mine` 판정이다.** `decide`는 스탬프의 device가 자기 것과 같으면 파일 내용을 행보다 우선해 채택하고 아무것도 기록하지 않는다(§6). 그래서 충돌은 순서가 어긋나는 정도가 아니라 한 기기가 다른 기기의 글을 조용히 가져가는 사고다. 4자는 기기 둘에서 1/65,536, 열에서 약 1/1,400이고 8자는 열에서 10^-8 수준이다. 유도가 "한 기계 = 한 writer"를 전제한다는 점도 같이 봐야 한다 — 한 기계에서 데이터베이스 둘이 같은 vault를 쓰면 둘의 id가 같아지고, 그때 서로의 파일이 정확히 이 분기에 걸린다.
- **블록 id (`yid`)**: 12자 base64url, `^[A-Za-z0-9_-]{12}$`. 9바이트를 `URL_SAFE_NO_PAD`로 인코딩한 것이라 padding도 modulo 편향도 없다([id.rs:14-47](../../crates/notes-core/src/id.rs#L14)). **id 규칙은 하나다** — 도메인·파일·폴더 이름이 같은 값을 쓰고 유일한 예외가 home의 리터럴 `root`다. **대소문자를 접지 않는다**: base64url에서 `a`와 `A`는 다른 글자라 `Nd0000000abc`와 `Nd0000000ABC`는 두 블록이고 파일 내 유일성 검사도 파생 id 계산도 적힌 대로 읽는다. 접으면 합법인 문서가 중복이라는 이유로 거절된다. 복제 자식 id는 uuid v5로 파생한다 — 네임스페이스는 고정값 `7f9c2b14-5d63-4a08-9e21-3c6f0d8b4a52`, 이름은 `<부모 새 id>/<순번>`이고 결과 16바이트의 앞 9바이트를 인코딩해 `yid`로 만든다([tree.rs:39-46](../../crates/notes-core/src/tree.rs#L39)). 결정적이라 난수원 없이 core에서 만들 수 있다. 부모 id를 네임스페이스로 쓰지 않는 이유는 그 형태에 의존하지 않기 위해서다.

**순번은 복사가 원본 서브트리를 훑는 순서다.** 훑기는 서브트리 루트에서 시작하는 **깊이 우선 문서 순서**이고, 형제는 sort_key 오름차순(동률이면 id 오름차순)으로 들어간다. **삭제된 행과 그 아래 전체는 훑지 않는다** — 복사는 살아 있는 것만 가져간다. 순번은 루트를 빼고 **1부터** 센다(루트는 명령이 준 id를 그대로 쓴다). 네임스페이스·이름 형식·앞 9바이트·훑는 순서 넷 중 무엇이 바뀌어도 같은 복제가 다른 id를 내므로, 넷 다 이 문단이 고정하는 계약이다.
- **캡** (불변 규칙 8): 파일 16MiB, depth 128, 노드 20,000, 필드 100,000바이트. **도메인도 같은 상한을 건다** — DB에는 들어가는데 파일로는 못 나가는 값이 있으면 그 문서가 조용히 동기화에서 빠진다.
- **결정성**: 같은 DB 상태는 같은 바이트다. BTreeMap 또는 명시 정렬만, HashMap 순회 금지.
- `sort_key`는 frontmatter 외에는 파일에 쓰지 않는다. 형제 순서 = 줄 순서. 파서는 형제 순번으로 `ordinal * SORT_KEY_STEP`(4,294,967,296, [node.rs:5](../../crates/notes-core/src/node.rs#L5))을 재구성하고 병합이 실제 키를 정한다. **ordinal은 1부터다** — 첫 형제가 `1 * SORT_KEY_STEP`이다.

**이스케이프는 글자가 아니라 자리로 정한다.** 마침표는 문장 가운데서는 마침표이고 줄 앞에서는 목록 표시의 일부다 — 글자만 보고는 어느 쪽인지 알 수 없으므로 `escape_markdown`은 값이 놓이는 자리를 인자로 받는다([render.rs:363-517](../../crates/notes-sync/src/render.rs#L363)). 어디서나 escape하는 것은 셋뿐이고 각자 이유가 있다: `\`→`\\`(이게 없으면 나머지를 되돌릴 수 없다), `&`→`&amp;`(없으면 사용자가 친 `&lt;`가 왕복에서 `<`로 무너진다), `<`→`&lt;`(없으면 **사용자가 친 `<!--`가 주석 채널로 들어간다**). 그 밖의 ASCII 문장부호 — 마침표·쉼표·슬래시·더하기·괄호, 문장 안의 `-`·`*`·`_`·백틱 — 는 그냥 글자다.

| 자리 | 추가로 붙는 `\` |
|---|---|
| 줄 첫 글자 (블릿 본문의 첫 조각, note 줄) | 그 줄에서 블록을 여는 표시 하나 앞에 하나. `[ ]`·`[x]`, 선두 `-`·`*`·`+`·`#`, `[`가 뒤따르는 `!`, fence ` ``` `·`~~~`, 가로줄(`-`·`*`·`_` 셋 이상), 선두 숫자열(최대 9자리)을 닫는 `.`이나 `)`. 표시 앞 공백은 3칸까지 허용하고(4칸부터는 markdown이 코드 블록으로 읽어 열리는 블록이 없다) 백슬래시는 **표시 바로 앞**에 붙는다 — `1. `은 `1\. `이 된다 |
| 헤딩 | `![`로 시작할 때만. 헤딩 자리에서는 아무것도 블록을 열지 않지만 파서가 `![`로 시작하는 제목을 이미지로 읽고 거절한다(§5.2) |
| 링크 label | `[`→`\[`, `]`→`\]`. `]`가 label을 일찍 닫는다 |
| 줄 중간 | 없다 |

`>`는 어느 자리에서도 escape하지 않는다 — note가 자기 `> `를 앞에 쓰고 파서가 `>` 하나와 공백 하나를 다시 떼므로 둘째 `>`는 글자로 살아 돌아온다. 이 포맷이 `>`를 글자 아닌 것으로 읽는 자리는 없다.

`[ ]`·`[x]`는 모양이 아니라 **파서 때문에** 막는다. 파서가 `- [ ] `와 `- [x] `를 줄 앞에서 떼므로 본문이 그렇게 시작하는 블릿은 todo로 돌아오면서 세 글자를 잃는다. 본문이 정확히 `[ ]`이면 더 나쁘다 — 줄이 `- [ ] <!-- yid: … -->`가 되어 경계 검색이 뗄 주석을 못 찾고 노드가 자기 id를 본문으로 삼킨다. `[X]`가 목록에 없는 것도 같은 이유다: 파서가 그 모양은 떼지 않는다. 이 목록은 파서를 따라가고 둘은 같이 움직인다. fence와 가로줄은 파서가 글자로 되돌려 주므로 왕복에는 안전하다. 그런데도 막는 이유는 손대지 않은 ` ``` `가 사람이 파일을 연 편집기에서 나머지 전부를 삼키기 때문이다.

`escape_inline`은 개행 정규화 후 조각마다 `escape_markdown`하고 리터럴 `\n`으로 join한다. 첫 조각만 자기 자리를 쓰고 나머지는 줄 중간 자리다 — join 뒤에는 아무것도 줄 첫 글자가 아니다. 링크 label에서는 조각 전부가 label 자리다.

복원은 한 번의 좌→우 스캔이다([parse.rs:809-855](../../crates/notes-sync/src/parse.rs#L809)): 엔티티 3종(`&amp;`·`&lt;`·`&gt;`)을 되돌리고, `\`+ASCII 문장부호를 벗기고, inline 자리에서만 리터럴 `\n`을 개행으로 되돌리며, 짝 잃은 `\`는 그대로 둔다. 렌더러가 더는 `&gt;`를 만들지 않아도 되돌리는 쪽은 남는다 — 사용자가 친 `&gt;`는 `&`가 엔티티가 되면서 왕복한다. 성립하는 성질은 `unescape(escape(v)) == v` 하나이고 반대 방향은 성립하지 않으며 요구되지도 않는다(`\.` → `.` → `.`). **파일이 정본이 아니라 값이 정본이다.** 손편집 파일을 정규형으로 되돌리는 것은 §6의 되쓰기가 한다.

### 4.2 문서 전체 형태

```
---
<frontmatter>
---
# <escape_inline(문서 루트의 text)>
<루트 note — depth-0 blockquote, 비면 블록 생략>
<빈 줄 1개 — 항상>
<노드 라인들>
<빈 줄 1개>
<!-- yonalist
<블록마다 한 줄 — §4.3의 footer>
-->
```

**frontmatter** — 아래 순서대로, **기본값인 선택 키는 생략한다**. `키: 값` 한 줄씩, 콜론 뒤 공백 1개.

| # | 키 | 값 | 필수 | 기본값 |
|---|---|---|---|---|
| 1 | `kind` | `yonalist-notes` 또는 `yonalist-trash` | 필수 | — |
| 2 | `format_version` | `1` | 필수 | 없거나 다르면 격리 |
| 3 | `id` | 문서 루트의 블록 id. **home 문서만 리터럴 `root`** | 필수 | 없으면 격리 |
| 4 | `parent` | 부모 노드의 블록 id | 분할 문서만 | 없으면 페이지 문서 — home은 `id`가 가른다 |
| 5 | `sort_key` | i64 10진 | 선택 | `0`. 부모 문서의 줄 순서가 이긴다 |
| 6 | `max_hlc` | HLC | 렌더 필수 | 파스는 언제나 내용에서 다시 계산한다. 적힌 값은 아래 한 질문에만 쓴다 |
| 7 | `updated` | `max_hlc`의 시각을 파일 쓴 기기의 지역 시각으로 적은 `YYYY-MM-DDTHH:MM:SS±HH:MM` | 렌더 필수 | 파생값이라 읽지 않는다. 없어도 손으로 고쳐도 다음 렌더가 다시 만든다 |
| 8 | `root_hlc` | HLC | 렌더 필수 | 파스에서 없으면 `''` |
| 9 | `root_marker_kind` | `bullet`\|`todo`\|`ordered` | 선택 | `bullet` |
| 10 | `root_ordered_start` | i64 10진 | 선택 | `1`. `root_marker_kind: ordered`일 때만 나온다 |
| 11 | `root_collapsed` | `true`\|`false` | 선택 | `false` |
| 12 | `root_completed` | `true`\|`false` | 선택 | `false` |
| 13 | `root_starred` | `true`\|`false` | 선택 | `false` |
| 14 | `device_id` | 파일을 쓴 기기의 HLC device — 소문자 hex 8자 | 선택 | 모양이 다르면 없는 것으로 읽는다 |
| 15 | `device_name` | 파일을 쓴 기기의 이름, 200바이트까지 | 선택 | `device_id`와 짝이다. 한쪽만 없거나 이름이 200바이트를 넘으면 둘 다 없는 것으로 읽는다 |
| — | (미지 키 보존분) | 원문 라인 | — | 인정 키 전부 뒤, 닫는 `---` 앞 |

**문서 루트의 상태는 frontmatter가 전부 진다.** 헤딩에는 주석을 달 자리가 없고, 그래서 문서 루트는 footer에도 줄을 갖지 않는다.

**제목은 `#` 헤딩 하나가 진실 소스다.** frontmatter에 제목 키를 두지 않는다 — 헤딩이 이미 절단되지 않은 원본을 싣고 있어 사본을 둘 이유가 없다. 사본을 두면 우선순위 규칙과 수리 경로, 그리고 이스케이프 스킴 두 벌이 따라온다. boolean은 소문자 `true`/`false`만. 인정 스칼라 키의 중복은 격리다. **빈 HLC로는 렌더하지 않는다** — `max_hlc: `처럼 후행 공백으로 끝나는 줄은 손편집기의 trim에 사라지고 `git diff --check`에도 걸리므로, 스탬프 없는 문서는 파일을 쓰지 않고 오류로 보고한다.

**`updated`는 스탬프를 사람이 읽는 표기다.** base36 `max_hlc`는 파일을 연 사람에게 아무 말도 하지 않으므로, 같은 사실을 편집기·로그·달력이 다 아는 표기로 한 줄 더 쓴다. 적어 두는 것이 아니라 `max_hlc`에서 파생하므로 설명하는 스탬프와 어긋날 수 없다. **파일을 쓴 기기의 지역 시각으로 적고 offset을 함께 싣는다** — 편집한 사람이 보던 벽시계가 그대로 파일에 남고 offset이 붙어 있으니 어느 기기에서 읽어도 같은 순간을 가리킨다. 시간대가 다른 두 기기는 한 순간을 두 표기로 쓰지만 차이는 바이트에만 있다: 병합은 파일을 블록 단위로 비교하고 이 줄은 어느 블록에도 속하지 않아 남의 표기를 만나도 편집으로 읽지 않는다. 파일을 다시 쓰는 때는 문서가 바뀐 때이고 그때는 이 기기가 자기 자리를 말할 차례다. 파일에 적힌 값은 믿지 않는다: 손으로 고친 값은 교체되고, 이 키를 모르는 편집기가 지워 버린 파일은 다음 렌더에서 되찾는다.

**`device_id`·`device_name`은 기기 id에 이름을 붙일 유일한 근거다.** 스탬프는 기기를 hex 8자로만 부르고, 그 8자가 어느 노트북인지 말해 주는 자리는 포맷 어디에도 없었다. 그래서 파일을 쓴 기기가 자기 id와 이름을 함께 적고, 파일을 받은 기기는 그 짝을 배워 둔다 — 설정의 "Overwritten notes"가 진 쪽·이긴 쪽 기기를 이름으로 부르는 근거가 이것이다. 성질은 `updated`와 같다: 파일을 쓴 기기가 자기 자리를 말하는 줄이고, 어느 블록에도 속하지 않아 남의 값을 만나도 병합이 편집으로 읽지 않으며, 다음 렌더가 다시 만든다. 이름이 바뀌면 그 기기의 다음 방출이 새 이름을 싣고, 받은 쪽은 마지막으로 배운 이름을 쓴다. **둘 중 하나라도 비면 아무것도 쓰지 않는다** — 이름만 있는 줄은 아무 기기도 가리키지 않고, 빈 값은 `max_hlc`와 같은 이유로 후행 공백 줄이 된다. 이름이 한 줄에 들어가지 않으면(줄바꿈이 들어 있으면) 역시 쓰지 않는다: 화면에는 이름 대신 id를 보일 답이 이미 있다.

**읽는 쪽은 이 두 키를 남의 주장으로 읽는다.** 파일은 다른 기기가 쓴 것이고, 값은 기기 id로 키를 잡은 표에 들어간다. 그래서 `device_id`가 스탬프가 실을 수 있는 모양(소문자 hex 8자)이 아니면 기기를 가리키지 않는 값이므로 짝 전체를 버린다 — 받아 두면 어느 스탬프와도 만나지 않는 행이 남는다. 이름이 200바이트를 넘으면 이름이 아니라고 보고 역시 버리며, id는 그대로 화면에 나온다. 표가 커질 수 있는 상한이 파일 하나가 말할 수 있는 양이 아니라 id 공간(hex 8자)이 되는 것이 이 규칙의 값이다. **파일이 이 기기 자신의 id를 주장해도 이 기기 이름은 바뀌지 않는다**: 8자를 기계에서 유도해도 두 기기가 같은 값을 뽑는 일이 아주 드물게 남아 있고, 남의 말로 자기 이름을 바꾸면 그 뒤로 이 기기가 쓰는 모든 파일에 그 이름이 실린다. 이 기기 이름은 기기 자신에게서만 온다. `trash.md`는 이 키를 싣지 않는다 — trash를 쓰는 기기는 페이지도 쓰므로 페이지에서 배우는 것으로 충분하다.

**`max_hlc`는 두 번 읽힌다.** 문서가 밖으로 내놓는 값은 언제나 **내용에서 다시 계산한** 것이다 — 이 값이 부팅 클록을 시드하므로 손편집으로 미래로 밀린 키를 믿으면 그 뒤 모든 로컬 편집이 미래 스탬프를 받는다. 적힌 값은 **"이 파일이 얼마를 담고 있어야 했나"** 하나에만 쓴다. 노드 스탬프가 전부 footer에 있어서 파일 꼬리가 잘리면 증거도 같이 잘리고 내용은 거의 아무것도 아닌 값으로 합산된다. 그때 파일이 짧다고 말해 주는 것은 살아남은 frontmatter뿐이다. 둘 중 큰 값이 그 질문의 답이고([document.rs:49-51](../../crates/notes-sync/src/document.rs#L49)) 병합은 그 답으로 되쓰기 필요를 판정한다. 부풀린 값이 부르는 결과는 되쓰기 한 번이라 안전한 방향이다.

**루트 note**: 헤딩 직후 depth-0 blockquote. 줄마다 `> {escape_markdown(줄)}`, 빈 줄은 `>` 단독. note가 비면 블록을 생략한다. 블록(또는 헤딩) 뒤에 빈 줄 1개를 항상 렌더하고, 파서는 빈 줄 없이 바로 bullet이 와도 수용한다.

`trash.md`는 헤딩도 루트 note도 갖지 않는다(§4.6) — 닫는 `---` 다음 줄이 바로 첫 노드 라인이다.

### 4.3 노드 라인과 footer

한 블록은 두 자리에 적힌다. **본문 줄은 자기가 어느 블록인지만 말하고** 병합이 필요한 나머지 — 스탬프, 자리 주장, markdown이 그릴 표기가 없는 상태, 그림의 치수 — 는 파일 끝 footer 한 덩이로 간다. 노트를 읽으러 온 사람은 그 아래를 볼 일이 없다. 두 자리로 나눈 이유가 그것이다.

depth d의 들여쓰기는 공백 `2*d`개.

```
{들여쓰기}{프리픽스}{본문} <!-- yid: <블록 id> -->
```

**프리픽스**:

| marker | completed | 프리픽스 |
|---|---|---|
| todo | false | `- [ ] ` |
| todo | true | `- [x] ` |
| bullet·ordered | 무엇이든 | `- ` |
| split 줄 | 무엇이든 | `- ` (§4.5) |

**체크박스가 todo의 유일한 권위다.** 체크박스는 todo marker의 표기이고 footer는 `todo`를 **다시 쓰지 않는다** — 한 비트에 자리가 둘이면 둘이 어긋날 수 있고, 파서는 이미 접두사를 토큰보다 앞세운다. 체크박스로 만들지 않은 블릿은 완료 상태와 무관하게 그냥 블릿 텍스트로 나간다. 읽는 사람이 `- [x]`를 봤다면 그것은 언제나 체크한 할 일이다. `completed`는 marker와 독립이라([command_execution.rs:467](../../crates/notes-core/src/tree/command_execution.rs#L467)이 marker를 보지 않는다) todo가 아닌 노드도 완료일 수 있고, 그 상태는 footer의 `done`이 싣는다.

**번호 목록도 `- `로 그린다.** markdown은 번호를 그릴 수 있지만 `ordered_start`는 **그 행이 입력된 번호**이고 화면에 그려지는 번호가 아니다. 그려지는 번호는 run 전체의 함수라, 세어 올린 번호를 본문에 적고 그대로 읽어 들이면 run의 둘째 행부터 저장된 값이 바뀐다. 그 변화는 병합이 보는 내용 변화이므로 모든 기기가 서로의 파일을 끝없이 되쓴다. 저장된 값을 그대로 적는 길도 막혀 있다: markdown에는 음수나 열 자리를 넘는 번호를 적을 표기가 없고 도메인은 그런 값을 실제로 만든다. 그래서 번호는 footer가 진다. **markdown 서버에서 번호 행이 블릿으로 보이는 것이 그 대가이고 받아들이는 한계다.**

**본문과 주석의 경계**: 줄의 **마지막** ` <!--`에서 자르고 구분 공백 1개만 소비한다([parse.rs:504-519](../../crates/notes-sync/src/parse.rs#L504)). 주석 뒤의 공백은 편집기의 것이라 벗겨 내고 주석 **앞의** 공백은 본문의 것이라 그 자리에 남는다. 닫히지 않는 주석은 자르지 않고 본문에 그대로 둔다 — 그것도 사용자의 바이트이고 깨진 `yid:`를 버리면 노드가 새 정체성을 받는다. 본문이 비면 프리픽스 뒤 공백 1개 다음 바로 주석이 온다. 헤딩의 본문이 비면 `#` 뒤에 아무것도 쓰지 않고 후행 공백도 남기지 않는다.

**노드 note**: bullet 라인 다음 줄부터 `{공백 2*(d+1)}> …` blockquote, 루트 note와 같은 줄 규칙.

#### footer

```
<!-- yonalist
yid: <블록 id> <토큰>*
yid: <블록 id> <토큰>*
-->
```

- 여는 줄은 `<!-- yonalist`, 닫는 줄은 `-->`다. 렌더러는 파일의 마지막 덩이로 쓰고 앞에 빈 줄 1개를 둔다.
- 문서마다 정확히 하나. **노드가 없는 문서에도 빈 footer를 쓴다** — 모양이 하나면 렌더러도 파서도 분기가 없다.
- 항목 줄 하나가 블록 하나다. 첫 토큰은 반드시 `yid:`이고 그 값이 본문 줄과 이어 붙는 join key다. 문서 루트는 항목을 갖지 않는다(§4.2).
- 항목 줄의 순서는 본문 줄 순서 — 렌더러가 트리를 훑는 순서 그대로다.
- 파서 쪽 관용(구분자 trim, footer의 위치, 본문에 없는 블록의 항목)은 §5.1이, 거절 조건은 §5.2가 소유한다.

**토큰** — 공백 1개로 구분한다. 순서 고정, 각 토큰은 조건이 맞을 때만 나온다.

| 순서 | 토큰 | 조건 |
|---|---|---|
| 1 | `yid: <블록 id>` | 항상 |
| 2 | `t: <hlc>` | 항상. 렌더에서 비어 있으면 오류 — 스탬프 전 노드는 나가지 않는다 |
| 3 | `star` | starred |
| 4 | `ordered: <i64>` | marker가 ordered. `todo`는 쓰지 않는다 — 본문의 체크박스가 진다 |
| 5 | `done` | completed이고 marker가 todo가 아닐 때 |
| 6 | `split` | 이 줄이 분할 문서로 나간 자식을 가리킬 때 (§4.5) |
| 7 | `prev: <앞형제-id 또는 빈 값>@<hlc>` | 자리 주장이 (바로 앞 형제 줄의 id, 이 노드의 `t:`)와 다를 때 |
| 8 | `from: <parent>@<i64>` | `trash.md` 전용 (§4.6) |
| 9 | `collapsed` | collapsed |
| 10 | `w: <u32> px: <u32>x<u32> bytes: <u64>` | 이미지 노드 (§4.4). 셋이 이 순서로 함께 나온다 |
| 11 | (미지 토큰 보존분) | §5.3 |

split 줄의 항목은 `yid:`·`t:`·`split`, 그리고 조건이 맞을 때의 `prev:`가 전부다 — 상태 토큰을 쓰지 않는 이유는 §4.5가 적는다.

**토큰 분해 규칙**: 토큰은 공백으로 나눈 단어 단위로 인식한다. `:`로 끝나는 토큰은 **인정·미지를 가리지 않고 다음 단어 하나를 값으로 소비**하며, 그 값 자리는 인정 토큰으로 보지 않는다. 이 규칙이 없으면 `foo: collapsed` 같은 미지 토큰의 값이 상태로 오인된다. 같은 항목 줄에서 같은 인정 토큰이 두 번 나오면 격리다. 본문 줄 끝의 `<!-- … -->`도 같은 함수가 읽으므로 두 자리가 토큰의 뜻을 다르게 알 수 없다 — 다만 렌더러가 그 자리에 쓰는 것은 `yid:` 하나뿐이다.

**`prev`는 노드의 자리 주장이다** — 이 노드가 어느 형제 뒤에 있다고 언제 주장했는지를 (값, HLC) 켤레로 싣는다. 빈 값은 "첫 형제"다. 한 단어이고 마지막 `@`에서 가른다. 주장이 (바로 앞 형제 줄의 id, 노드 자신의 `t:`)와 같으면 **생략한다** — 생성 순서 그대로인 문서에는 이 토큰이 하나도 없고, 이동이 파생 위치와 실제 주장을 갈라놓은 노드에만 남는다. 주장의 HLC가 비어 있으면 아직 아무도 자리를 주장하지 않은 것이라 이때도 생략한다. **토큰이 없으면** 병합이 (앞 줄의 id, 이 노드의 `t:`)로 채운다. 토큰이 있는데 `@`가 없거나 왼쪽이 블록 id가 아니면 격리다 — 자리 주장을 추측하면 남의 줄 뒤로 노드를 옮긴다. HLC만 읽히지 않을 때는 빈 스탬프가 되어 모든 비교에서 진다. 값이 가리키는 id가 파일 안에 없어도 격리하지 않는다 — 부모를 건너 옮겨진 노드의 옛 이웃이 정상적으로 그런 값을 든다. 병합 규칙은 설계 문서 §7.6이 소유한다.

### 4.4 이미지 라인

이미지 노드도 본문 한 줄이 전부이고 그 줄이 지는 것은 링크와 alt 텍스트다. 치수는 그 블록의 footer 항목이 진다.

```
{들여쓰기}{프리픽스}![{escape_inline(원본명)}]({상대 경로}) <!-- yid: <블록 id> -->
```

```
yid: <블록 id> t: <hlc> w: <u32> px: <u32>x<u32> bytes: <u64>
```

- **상대 경로**는 §3.4를 따른다. 경로 탈출과 비정규 형태는 격리한다. 확장자는 `png`·`jpg`·`jpeg`·`gif`·`webp`만 수용한다.
- `w:`는 표시 폭, 하한 120([image.rs:9](../../crates/notes-core/src/image.rs#L9)). `px:`는 원본 픽셀 크기로 두 값 다 0보다 커야 하고 `bytes:`는 1 이상 20MiB 이하다. 범위를 벗어난 값은 격리다 — 이 상한은 포맷의 사실이므로 이유를 말할 수 있는 여기서 답하고 DB 제약이 아무 말 없이 죽는 자리까지 끌고 가지 않는다.
- **원본 파일명은 링크 텍스트가 진다.** v1이 percent 인코딩해 주석에 싣던 값을 사람이 읽는 자리로 옮겼다 — markdown 서버에서 alt 텍스트로 그대로 보인다. alt가 비어 있으면(`![](…)`는 어느 markdown 편집기나 쓴다) 경로의 파일 이름을 이름으로 삼는다.
- **손으로 넣은 이미지 줄은 문서를 격리한다.** 치수가 footer에 있고 footer는 줄의 `yid:`로 이어 붙으므로, 사람이 타이핑한 `- ![pic](assets/x.png)`은 이어 붙일 항목이 없어 치수를 얻지 못한다. 기본값으로 받을 길도 없다 — `notes_images`가 픽셀 0과 바이트 0을 거절하고, 추측으로 행을 만들면 앱이 이미 들고 있는 바이트 위에 placeholder를 그린다. **받아들이는 한계다.** 거절 문장은 사람이 손댈 자리를 가리키도록 footer와 그 파일 이름을 말한다.
- 자산 바이트가 아직 도착하지 않아도 **메타가 완전하면 노드를 적용한다**([image.rs:90-114](../../crates/notes-core/src/image.rs#L90)의 `try_referenced`). placeholder는 메타가 불완전할 때만이고, 그 줄은 다음 방출에서 원문 그대로 재방출한다. 해소 시 표시 폭이 없으면 `DEFAULT_DISPLAY_WIDTH`(320, [image_assets.rs:16](../../crates/notes-sqlite/src/image_assets.rs#L16))를 쓴다.
- **문서 루트가 이미지 노드인 경우는 문법 밖이다.** 헤딩에 이미지를 실을 자리가 없다. 그런 상태는 방출에서 격리하고 상태로 통지한다. 그래서 헤딩만은 `![`를 escape한다(§4.1) — 그렇게 시작하는 제목이 이미지로 읽히지 않게.

### 4.5 분할

문서가 §7의 임계를 넘으면 직계 자식 하나가 자기 폴더의 문서로 나간다. 부모 문서에는 평범한 markdown 링크 한 줄이 남는다.

```
{들여쓰기}- [{escape_inline(자식 제목)}]({폴더}/README.md) <!-- yid: <블록 id> -->
```

```
yid: <블록 id> t: <hlc> split
```

자식 문서의 frontmatter는 `parent`와 `sort_key`로 자기 자리를 기록한다. **본문 줄만으로는 split 줄과 링크를 담은 평범한 블릿이 구별되지 않는다** — 가르는 것은 footer의 `split`이고 그 토큰이 없는 줄은 링크 텍스트를 가진 평범한 블릿으로 읽는 것이 맞는 읽기다. `split`이 있는데 링크가 가리키는 문서가 없으면 격리하지 않고 **아직 못 받음**으로 두고 재시도한다 — 전파 순서 때문에 흔히 생기는 상태다.

**split 줄의 권위는 존재와 위치뿐이다.** 파서가 split 줄에서 취하는 증거는 노드의 존재, 형제 사이 위치(줄 순서와 `prev` 토큰 — 위치 권위가 이 문서에 있으므로 split 줄의 항목도 §4.3의 조건대로 `prev`를 싣는다), 링크 대상이다. 노드의 상태 — 제목·marker·별표·완료·접힘·hlc — 는 자식 문서의 frontmatter가 권위이고, 항목의 `t:`는 부모 문서 `max_hlc` 계산용 사본이다. 같은 노드가 두 파일에 실리므로 권위를 한쪽에 몰아야 병합 순서가 결과를 바꾸지 않는다(불변 규칙 2). 링크 텍스트는 표시용이라 낡아도 되고 다음 방출이 맞춘다. **split 줄에는 상태 토큰(`star`·`ordered:`·`done`·`collapsed`)을 쓰지 않고** 본문의 프리픽스도 언제나 `- `다 — 체크박스도 상태를 말하는 것이라 쓰지 않는다. 손으로 넣은 상태가 그 항목에 있어도 파서가 기본값으로 되돌린다.

### 4.6 `trash.md`

```
---
kind: yonalist-trash
format_version: 1
max_hlc: <hlc>
updated: <max_hlc의 시각>
---
- Deleted <!-- yid: <블록 id> -->
  - Child <!-- yid: <블록 id> -->

<!-- yonalist
yid: <블록 id> t: <hlc> from: <parent>@<sort_key>
yid: <블록 id> t: <hlc> done
-->
```

바이트는 §11의 B가 싣는다.

- **trash 루트** = `deleted = 1`이고 부모가 살아 있거나 없는 노드. `from:`의 parent는 블록 id이거나, 삭제된 노드가 페이지였으면 리터럴 `root`다. 값은 sort_key다.
- trash 루트의 정렬은 `(sort_key, id)` 오름차순. 자식은 `from:`을 쓰지 않는다 — 부모가 같이 왔으므로 자리를 안다.
- trash 루트 항목은 `prev`를 싣지 않는다 — 자리는 `from:`이 이미 준다. 자식 항목은 §4.3의 조건대로 싣는다.
- `trash.md`는 헤딩도, 루트 note도, `id`도 갖지 않는다 — 닫는 `---` 다음 줄이 바로 첫 노드 라인이다. 격리 상태는 리터럴 키 `yonalist-trash`로 기록한다.
- trash 항목이 하나도 없으면 `trash.md`를 쓰지 않고, 있던 파일은 지운다. 파일 부재 = 삭제 없음.
- frontmatter 미지 키는 실을 노드 행이 없어 보존하지 않는다. 손으로 넣은 키는 다음 렌더에서 사라진다.
- 이미지 라인은 언제나 `../assets/…`를 가리킨다 — 휴지통에 들어간 이미지의 바이트는 루트 저장소로 승격돼 있다(§3.3).

## 5. 파서

### 5.1 수용

| 입력 | 처리 |
|---|---|
| yid 없는 bullet | 수용. id 없음으로 통과 — 발급은 병합 몫이고 write-back으로 역기록한다 |
| footer가 없거나 비어 있다 | 수용. 모든 노드가 빈 스탬프와 기본 상태로 읽힌다 — `t:` 하나를 지운 줄에 적용되는 규칙을 문서 전체로 늘린 것이다. 그 파일은 DB에 지고 다음 방출이 정규형을 되쓴다 |
| 블록의 footer 항목이 없다 | 같다. 빈 스탬프와 기본 상태. 이미지 줄만 예외로 격리한다(§4.4) |
| 항목의 `t:` 없음 또는 HLC 파싱 불가 | `''` → LWW에서 언제나 패배 |
| 본문에 없는 블록의 footer 항목 | **버린다.** 손으로 블릿을 지우면 남는 정상 상태다. 문서 안에 담아 둘 자리도 없다. 파스가 버리고 렌더가 쓰지 않으므로 두 번째 왕복이 같은 바이트다 |
| footer가 파일 끝이 아닌 자리에 있다 | 수용. 덩이만 잘라내고 남은 줄이 순서 그대로 본문이다 — 파일 끝에 한 줄 덧붙이는 것이 가장 흔한 손편집이고 편집기에서 그러는 사람이 저 아래 주석이 살림살이라는 것을 알 이유가 없다. 헤딩 앞에 있어도 같다. 렌더러는 언제나 마지막에 쓴다 |
| 구분자·항목 줄의 앞뒤 공백 | 수용. 구분자는 trim해서 맞추고 항목 줄은 들여써도 읽는다 — 후행 공백은 편집기의 것이고 포맷의 것이 아니다. 눈에 보이지 않는 글자 하나가 문서 전체를 잃게 하지 않는다 |
| 홀수 칸·탭 들여쓰기 | 2칸 내림 정규화, 탭 = 2칸. 예상보다 깊은 bullet은 가장 가까운 depth로 clamp |
| 들여쓰기가 어긋난 note 줄 | 바로 위 줄의 note로 붙는다. 렌더러는 note를 자기 블릿 바로 아래에만 쓰므로 조상 depth의 note는 손편집이고 조상의 것으로 읽으면 사람이 둔 자리에서 글이 옮겨진다 |
| checkbox 없는 `- text` | marker = bullet, completed = false |
| `- [ ]` · `- [x]` | marker = todo, completed는 표시대로. 접두사가 footer의 토큰보다 앞선다 |
| 선택 frontmatter 키 누락 | §4.2 기본값 |
| 미지 frontmatter 키·footer 토큰 | **보존** (§5.3) |
| CRLF | LF 정규화 |
| 공백뿐인 본문 줄 | 빈 줄 취급 |
| 닫히지 않는 줄 끝 주석 | 자르지 않고 본문에 남긴다 (§4.3) |
| `split` 링크가 가리키는 문서 부재 | 아직 못 받음 — 재시도 |

### 5.2 격리

**격리는 문서 전체 거부다. 절반만 적용된 결과가 존재하면 그 자체가 결함이다.** 통지는 `notes://sync-status`, 병합은 skip한다.

| 입력 |
|---|
| `format_version`이 `1`이 아니거나 없다 |
| `id` 누락 — 또는 `id`·`parent`·`yid:`·`prev:`·`from:`이 든 값이 블록 id가 아니다. 문서 루트의 리터럴 `root`와 `from: root@…`만 예외 |
| `prev:`·`from:`에 `@`가 없다. `sort_key`·`root_ordered_start`·`ordered:`가 i64가 아니다. `root_*` boolean이 `true`/`false`가 아니다. `root_marker_kind`가 세 값 밖이다 |
| UTF-8이 아니거나 16MiB 초과 |
| depth > 128 / 노드 > 20,000 / 필드 100,000바이트 초과 |
| `<<<<<<<` 또는 `>>>>>>>`로 시작하는 라인 (git 충돌 마커) |
| 인정 스칼라 키 중복, 한 footer 항목 안의 인정 토큰 중복, 파일 내 yid 중복(**대소문자 구분** — §4.1), 문서 id와 노드 id 충돌 |
| footer가 둘 이상이다 |
| footer가 닫히지 않는다 — 여는 줄만 있고 `-->`가 없다 |
| footer 항목 줄이 어느 블록인지 말하지 않는다 (`yid:` 값 없음) |
| 같은 블록을 footer가 두 번 말한다 |
| 비정규 자산 링크 — 경로 탈출, `assets/` 밖을 가리킴, `assets/` 아래 하위 폴더, 이미지가 아닌 확장자 |
| 이미지 줄인데 footer 항목의 `w:`·`px:`·`bytes:`가 없거나 범위를 벗어난다 (§4.4) |
| kind 비호환 키 — 페이지 문서에 `from:`, trash에 `id:` |
| 소화되지 않는 본문 줄 — bullet도 note도 아니다 |
| 문서 루트가 이미지 노드다 |

**footer가 반쯤 읽히는 것은 없는 것보다 나쁘다** — 어떤 블록이 남의 상태를 들고 돌아왔는지 아래쪽에서 알 방법이 없다. 그래서 footer의 형식 위반은 문서 전체 거부다. 반대로 **정보가 모자란 것은 관용한다** — footer가 없는 것, 블록의 항목이 없는 것, 항목이 가리킬 줄이 없는 것은 전부 §5.1이 수용한다.

**그 밖의 구조 위반도 전부 격리한다.** 위 표는 자주 만나는 것을 적은 것이지 전수가 아니다. 파서가 문법으로 설명할 수 없는 줄을 만나면 문서를 거부한다.

### 5.3 미지 조각 보존

파서는 자기가 의미를 갖지 않는 조각을 원문 그대로 실어 나른다. 앞으로 포맷이 늘어날 때 먼저 만들어진 파일이 값을 잃지 않게 하는 장치다. 저장처는 `notes_nodes.sync_extras`이고 컬럼 인코딩은 구현 소유다. 파일 쪽 계약만 고정한다:

| 조각 | 보존 단위 | 재방출 위치 | 순서 |
|---|---|---|---|
| frontmatter 미지 키 | `키: 값` 라인 전체 | 인정 키 전부 뒤, 닫는 `---` 앞 | 만난 순서 |
| footer 항목의 미지 토큰 | §4.3의 분해 규칙으로 잘라 낸 토큰(값 포함) | 그 항목 줄의 인정 토큰 전부 뒤, 줄 끝 | 만난 순서 |

`updated`는 인정 키다 — 미지 키로 보존하면 렌더러가 자기 줄과 남의 사본을 같이 써서 왕복마다 한 줄이 늘어난다. 값을 읽지 않으면서 아는 키로 두는 이유가 그것이다.

이미지의 `w:`·`px:`·`bytes:`도 인정 토큰이라 미지 토큰은 그 셋 뒤에 온다. 미지 토큰 하나가 뒤따르는 인정 토큰을 밀어내지 않는다 — 분해 규칙이 값 소비를 토큰별로 정하기 때문이다.

같은 상태를 두 번 렌더하면 보존분 포함 바이트가 같다. 보존은 바이트가 아니라 정보를 지키는 것이라 재방출은 언제나 정규형이다.

## 6. 손편집

사용자가 다른 에디터로 vault 파일을 여는 것은 **정상 사용**이다. 무엇을 고쳤느냐에 따라 결과가 갈린다.

| 사용자가 한 일 | 결과 |
|---|---|
| **본문만 고치고 줄 끝 주석과 footer는 그대로 둠** | 정체성이 남아 있으니 같은 노드다. **탐지는 해시다** — 파일 해시가 `exported_hash`와 다르면 병합하고, 같은 t에 다른 내용이면 아래 규칙대로 푼다. 내 vault에서 벌어진 손편집은 병합이 아니라 **저작 행위**로 취급해 채택한 내용에 fresh HLC를 찍고 `needs_write_back`으로 정규형을 되쓴다 |
| 줄을 옮기거나 들여쓰기를 바꿈 | 구조도 같은 규칙을 탄다. 부모와 순서를 줄 위치에서 재구성하고 달라졌으면 fresh HLC로 채택한다 |
| 새 bullet을 손으로 추가 | yid 없는 줄로 수용되고, 병합이 블록 id와 HLC를 발급한 뒤 write-back한다 |
| 파일 끝에 한 줄 덧붙임 | footer 뒤에 붙어도 본문으로 돌아온다(§5.1). 다음 방출이 footer를 다시 끝으로 옮긴다 |
| **줄 끝 주석을 지움** | 정체성을 잃어 신규 노드로 발급된다. 원본은 DB에 남아 있어 **중복이 생긴다.** 남은 footer 항목은 가리킬 줄이 없어 버려진다. 재결합은 이번 범위 밖이다 |
| footer를 지움 — 또는 전송 중 파일 꼬리가 잘림 | 모든 노드가 빈 스탬프로 읽혀 그 파일이 DB에 전부 진다. 잃는 것은 원격 변경의 도착이 아니라 한 번의 지연이고 frontmatter의 `max_hlc`가 파일이 짧다고 말해 주므로(§4.2) 다음 방출이 정규형을 되쓴다 |
| 파일 이름·폴더 이름을 바꿈 | 이름은 꾸밈이다. 안의 `id`로 같은 문서임을 알아보고 경로만 갱신한다 |
| 문법을 깨뜨림 | 문서 전체 격리. **그 파일을 덮어쓰지 않고** 사람이 볼 때까지 그대로 둔다 |
| 파일을 지움 | 부재는 삭제가 아니다. 다음 방출이 다시 쓴다 |

사용자에게 말할 때의 계약은 이 한 문장이다: **"본문은 아무 에디터로나 고칠 수 있고, 줄 끝의 주석은 그 줄의 정체성이라 지우면 새 항목이 된다."** 파일 끝 덩이는 앱의 살림살이라는 말을 덧붙이되, 지웠을 때 잃는 것이 한 번의 지연이라는 것도 같이 말한다. "평범한 markdown이라 마음대로"라고 말하지 않는다 — 그 기대 위반이 Logseq가 치른 값이다.

**변경 감지 — 이벤트는 무조건 해시, stat 단축은 전체 스캔에만.** 감시 이벤트를 받은 파일은 mtime·크기를 보지 않고 **바로 읽어 해시**하고, 해시가 `exported_hash`와 다르면 파싱한다 — 이벤트가 왔다는 것 자체가 "무언가 있었다"이고, Syncthing처럼 mtime을 보존하는 transport에서는 stat이 거짓 "무변경"을 준다. mtime·크기 단축 경로는 **전체 스캔(시작·60초 안전망)에만** 있다 — 수천 파일을 훑는 자리라 stat 없이는 비용이 서지 않고, 놓치는 경우는 "이벤트도 놓치고 stat도 보존된 변경"뿐이라 좁다. 그 잔여마저 사용자가 실행하는 "vault에서 다시 읽기"가 닫는다 — 수동 재색인은 stat을 무시하고 전 파일을 해시로 검증한다. **`max_hlc`는 파일 생략 근거가 아니다**: 손편집은 `t`도 `max_hlc`도 바꾸지 않으므로, HLC로 파일을 거르면 손편집이 영원히 무시된다. `max_hlc`는 병합 안에서 노드 비교를 줄이는 내부 최적화로만 쓴다.

**원격 파일의 같은 t 충돌은 내용이 가른다.** 원격에서 온 파일이 같은 `t`에 다른 내용을 실었다면(아직 재스탬프되지 않은 원격 손편집, 또는 16비트 기기 표식 충돌) fresh HLC를 발급하지 않는다 — 발급하면 병합 순서가 결과를 바꾼다. 대신 **정규화한 내용 해시가 큰 쪽이 이긴다** — 결정적이고 교환적이다. 진 쪽은 충돌 로그에 남는다. 손편집을 한 그 기기의 앱이 다음에 열리면 자기 vault에서 해시 불일치를 보고 fresh HLC로 재스탬프하므로, 손편집은 결국 정상 LWW 경로로 이긴다.

**방출이 손편집을 덮지 않게 하는 규칙.** 파일을 쓰기 직전에 현재 파일의 해시를 `exported_hash`와 대조한다. 다르면 그 사이에 누군가 고친 것이므로 **쓰지 않고 먼저 병합**한다. 이 검사가 없으면 사용자가 에디터에서 고친 내용을 우리 디바운스 방출이 덮는다. 대조와 이름 바꾸기 사이에 남는 좁은 창은 no-replace 이동(교체 대상의 identity 검증 — M1.3 file_io 계약)으로 마저 닫는다.

## 7. 분할과 크기

- 임계는 **256KB 또는 노드 2,000개**. 되돌려 합치는 것은 96KB·800개 밑으로 내려왔을 때다.
- 내보내는 대상은 가장 큰 자식이 아니라 **가장 오래 손대지 않은 직계 자식** — 그 서브트리의 `max_hlc`가 가장 작은 것. 자주 고치는 부분이 작은 파일에 남아야 편집 한 번의 비용이 준다. 문서의 15% 미만인 자식은 후보가 아니다.
- 되돌려 합칠 때는 반대로 가장 최근에 손댄 자식부터.
- 한 번에 한 단계만 자른다.
- **이번 이식에서는 포맷만 만든다.** 자동 승격은 켜지 않고 사용자가 실행하는 "문서로 분리" 명령만 둔다.

## 8. 불변 규칙

v1의 10건을 계승한다.

1. **부재 ≠ 삭제.** 파일에 없는 노드는 지우지 않는다. 삭제는 `trash.md` 이동이라는 증거로만 전파된다.
2. **병합은 멱등·교환적.** 같은 문서를 두 번 병합하면 no-op이고 순서가 결과를 바꾸지 않는다. 멱등 계약은 발급값이 write-back된 문서부터 적용된다.
3. **직렬화는 결정적.** 같은 상태 → 같은 바이트.
4. **방출은 자가 검증한다.** 쓴 바이트를 재파싱해 상태와 다르면 파일을 덮지 않고 dirty를 유지한다.
5. **원자적 쓰기만.** 임시 파일에 쓰고 이름을 바꾼다.
6. **명시 HLC는 재스탬프되지 않는다.** 트리거의 WHEN 가드가 보장한다.
7. **자산 경로는 정규형만.** 경로 탈출은 격리한다.
8. **캡을 지킨다.** 파일·depth·노드 수·필드 크기. 도메인과 파일이 같은 값을 쓴다.
9. **격리는 문서 전체.** 부분 적용 금지.
10. **병합과 부트스트랩은 history 없이 실행된다.** 원격 변경은 undo 스택에 들어가지 않는다.

v2 개정 3건:

- **A. 병합은 워커 큐를 지난다.** 별도 연결로 쓰면 프런트가 든 revision이 조용히 낡는다. 병합 트랜잭션은 **적용된 변경이 있을 때만** revision을 올린다.
- **B. undo 배리어.** 병합은 `NotesService::absorb_external`을 지나 서비스의 revision 사본을 갱신하고, 병합이 만진 노드(affected = 변경 ∪ 삭제)와 교차하는 undo 항목 위로 `undo_floor`를 올린다. 교차하지 않는 위쪽 항목은 전부 되돌아간다. redo는 교차 시 전체 비운다.
- **C. 이벤트 계약.** `notes://sync-changed { revision, changedNodeIds, deletedNodeIds }`와 `notes://sync-status`. 이 앱 최초의 Tauri 이벤트다.

## 9. 정책

- **HLC는 내용이 바뀔 때만 전진한다.** 방출 시 노드의 내용 해시를 직전 방출본과 비교해 같으면 그때의 HLC를 그대로 쓴다. 상태를 바꿨다 되돌린 편집이 파일을 건드리지 않게 하는 규칙이다.
- **미래로 튄 시계.** 로컬 시계보다 24시간 넘게 앞선 HLC는 fresh HLC로 재스탬프하고 기록한다. **그 값을 observe하지 않는다** — 흡수하면 이후 모든 로컬 편집이 미래 스탬프를 받아 정책이 무력해진다.
- **transport 겹침.** 같은 vault를 두 동기화 클라이언트가 만지는 구성은 문서로 금지하고, 감지되면 경고한다.
- **conflicted copy는 입력이다.** 우리 포맷이면 병합하고 정본 하나로 다시 쓴 뒤 사본을 `sync-cleanup`으로 치운다. 열어 봤을 때 `id`가 다르면 같은 문서의 두 판이 아니라 서로 다른 문서다 — 폴더 이름 규칙(§3.1)이 애초에 이 상황을 거의 없앤다.
- **자리표시 파일.** 내용이 아직 없는 파일은 삭제나 절단으로 읽지 않는다. 판별되면 병합하지 않고 재시도한다.
- **재색인 전에 방출한다.** 재색인은 파일을 진실로 채택하므로 미방출 편집이 남아 있으면 거부한다.
- **렌더 바이트를 바꾸는 릴리스는 `format_version`을 올린다.** 수렴 전체가 "같은 상태 = 같은 바이트" 위에 서 있다. 렌더러 출력이 한 바이트라도 다른 두 앱 버전이 한 vault를 공유하면, 서로의 파일을 "비정규형"으로 보고 끝없이 되쓰는 핑퐁이 된다 — `format_version`이 같아 격리도 안 된다. 그래서 출력 바이트가 달라지는 변경은 포맷 버전 승급이고, 구버전 앱은 새 파일을 격리하며 멈춘다. golden 바이트 테스트가 이 규율의 기계 검사다: golden이 깨지는 diff = 버전 승급이 필요한 diff. (개발 중에는 기기들이 같은 빌드라 발화하지 않는다 — 릴리스 규율이다.)
- **첨부 위치는 노드 내용이 아니다.** 링크 경로는 방출 시 첨부의 현 위치에서 파생한다. 승격·강등은 HLC를 전진시키지 않고, 가짜 충돌을 만들지 않는다.
- **사이클은 결정적으로 파킹한다.** 이동 병합이 고리를 만들면 고리 안에서 HLC가 가장 작은 이동의 노드를 복구 페이지 아래로 옮긴다. 복구 페이지의 id는 `uuid v5(sync_meta.vault_uuid, "yonalist-recovery-page")`의 앞 9바이트를 `yid`로 인코딩한 값이다 — `vault_uuid`는 블록 id가 아니고 파일에 나가지도 않으므로 UUID로 남는다. 제목은 "복구됨", 폴더 이름은 §3.1 그대로이고 필요할 때 lazy 생성한다. vault_uuid가 기기마다 달라 복구 페이지가 둘 생길 수 있고 LWW로 공존한다 — 계약은 "같은 입력이면 같은 노드가 파킹된다"이다.

## 11. golden

`crates/notes-sync/fixtures/`의 4종이 이 절의 바이트다 — 렌더러 출력이 그 파일과 바이트 단위로 대조되므로, 아래 블록이 곧 기계가 지키는 계약이다. 지어낸 값은 아래로 고정한다.

4종에는 `prev` 토큰(§4.3)이 하나도 없다 — 전부 생성 순서 그대로라 모든 노드의 자리 주장이 (앞 줄, 자신의 `t:`)와 같아 생략되기 때문이다. `updated`의 2041년도 지어낸 값이 아니라 지어낸 HLC의 millis를 읽은 결과다. 골든을 쓴 기기는 `+09:00`에 있다고 두었고 `updated`의 offset이 그 자리를 말한다 — 같은 순간을 UTC 기기가 쓰면 `2041-10-11T06:19:09+00:00`이 된다.

| 자리 | 값 |
|---|---|
| 페이지 id (Projects) | `PrJects00001` |
| 페이지 id (회의록) | `Mnutes000001` |
| 분할 문서 id | `Archive00001` |
| 노드 id | `Nd00000000NN` |
| device | `a3f2a3f2` |
| HLC | `0swkd7qz4-00-a3f2a3f2`부터 counter 증가 |
